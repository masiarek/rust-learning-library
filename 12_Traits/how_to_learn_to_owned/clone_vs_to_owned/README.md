# Step 1: `ToOwned` is `Clone` with a separate owned type

[How to learn `ToOwned`](../README.md) › **Step 1 of 10** · next: [Step 2 — Some types have no size](../types_with_no_size/README.md)

**Level:** 101 · a step on a learning path

**One line:** `Clone` turns a `&T` into another `T`; `ToOwned` turns a `&B` into a `B::Owned`, which may be a different type — a `&str` into a `String` — and the impl that does it sits on `str`, the type *behind* the `&`, not on `&str`.

## Two signatures

```rust
// Clone: the copy is the type you started with
fn clone(&self) -> Self;             // &String -> String

// ToOwned: the copy is whatever Owned names
fn to_owned(&self) -> Self::Owned;   // &str -> String
```

That is the whole difference, and the rest of the path is about why it has to exist. Here is the trait in full:

```rust
pub trait ToOwned {
    type Owned: Borrow<Self>;
    fn to_owned(&self) -> Self::Owned;
    fn clone_into(&self, target: &mut Self::Owned) { ... }
}
```

- `type Owned` is the one new idea: an **associated type**, a type the impl names. It is what lets `str`'s answer be `String`. How associated items work in general is on [What a trait is](../../what_a_trait_is/README.md#three-kinds-of-item-can-go-in-a-trait).
- `Borrow<Self>` is the way back from the owned type to the borrowed one — [step 7](../borrow_the_way_back/README.md).
- `clone_into` is a provided method that refills an owned value you already have — [step 9](../clone_into_refills/README.md).
- And notice what is *not* there. [`Clone` is declared `Clone: Sized`](../clone_returns_self/README.md); `ToOwned` is not, so its `Self` may be a type with no size, such as `str`. [Step 2](../types_with_no_size/README.md) is why that matters.

## The impl is on the type behind the `&`

| `Self` | `Self::Owned` | so `&self` is |
|---|---|---|
| `str` | `String` | `&str` |
| `[T]`, for `T: Clone` | `Vec<T>` | `&[T]` |
| `Path` | `PathBuf` | `&Path` |
| `OsStr` | `OsString` | `&OsStr` |
| `CStr` | `CString` | `&CStr` |
| any `T: Clone` | `T` itself | `&T` — the blanket impl, [step 6](../the_blanket_to_owned/README.md) |

Read the first row slowly, because it is the one most explanations blur: **`Self` is `str`, so `&self` is `&str`, and the result is a `String`.** A `&str` is the *argument*, not the implementing type.

One sentence you will meet gets this wrong: *"`&str` implements `ToOwned` to produce a `String`"*. It is `str` that does. Whether `&str` has a `ToOwned` of its own — it does, and it is not the one you want — is [step 6](../the_blanket_to_owned/README.md#one-str-two-impls)'s surprise, once steps 4 and 5 have put the pieces in place.

## Practice

**Write the function that hands back the owned twin.** Write `owner`, generic over a borrowed type `B`, that takes a `&B` and returns `B`'s owned type.
```rust
//! Kata solution for step 1: one generic function that hands back the owned
//! twin of whatever it is lent — and the argument's type decides which twin.
//!
//!   rustc --edition 2024 clone_vs_to_owned_kata.rs -o /tmp/cvtok && /tmp/cvtok

use std::any::type_name_of_val;
use std::ffi::OsStr;
use std::path::Path;

/// `?Sized` is what lets `B` be `str`, `[i32]`, `Path` or `OsStr`.
fn owner<B: ToOwned + ?Sized>(borrowed: &B) -> B::Owned {
    borrowed.to_owned()
}

fn main() {
    println!("One function, six arguments: the type of the argument picks B");
    let text: &str = "Ada";
    println!("   owner(text)                 B = str   -> {}", type_name_of_val(&owner(text)));
    println!("   owner(&text)                B = &str  -> {}", type_name_of_val(&owner(&text)));
    println!("   owner(&[1, 2][..])          B = [i32] -> {}", type_name_of_val(&owner(&[1, 2][..])));
    println!("   owner(Path::new(\"a.txt\"))   B = Path  -> {}", type_name_of_val(&owner(Path::new("a.txt"))));
    println!("   owner(OsStr::new(\"a.txt\"))  B = OsStr -> {}", type_name_of_val(&owner(OsStr::new("a.txt"))));
    println!("   owner(&7)                   B = i32   -> {}", type_name_of_val(&owner(&7)));

    println!();
    println!("The one that surprises: an extra & changes B, and so the answer");
    let same = owner(&text);
    println!("   owner(&text) is the same &str, same address: {}", std::ptr::eq(same, text));
}
```

Without `?Sized`, four calls fail with `E0277`, *"the size for values of type `str` cannot be known at compilation time"* (and the same for `[{integer}]` and `[u8]`, which is what `Path` and `OsStr` wrap): `owner(text)`, `owner(&[1, 2][..])`, `owner(Path::new(…))` and `owner(OsStr::new(…))` all need `B` to be unsized. `owner(&text)` and `owner(&7)` keep compiling, because `&str` and `i32` have a size — which is also why those two are the calls whose answers are not the owned type you expected. [Step 2](../types_with_no_size/README.md) is the `?Sized` half and [step 6](../the_blanket_to_owned/README.md) the `&str` half.

## Po polsku

`Clone` robi z `&T` kolejne `T` — ten sam typ. `ToOwned` robi z `&B` wartość typu `B::Owned`, który może być innym typem: z `&str` powstaje `String`. Najważniejszy szczegół tego kroku: implementacja jest na `str`, czyli na typie **za** referencją, a nie na `&str`. Skoro `Self` to `str`, to `&self` to `&str` — i dlatego `s.to_owned()` daje `String`, bez żadnej dereferencji.

Często powtarzane zdanie „`&str` implementuje `ToOwned`, dając `String`” jest więc błędne — robi to `str`. Czy `&str` ma własną implementację `ToOwned`? Ma, i nie jest to ta, której szukasz; to temat kroku 6, gdy kroki 4 i 5 będą już za tobą.
