# After the steps: `Clone`, `ToOwned` or `From`?

[How to learn `ToOwned`](../README.md) › **After the ten steps** · back: [Step 10 — Implementing it](../implementing_it_or_not/README.md)

**Level:** 201 · the path's last page

**One line:** `Clone` copies a `T` out of a `&T`; `ToOwned` builds an owner out of a borrow, possibly of another type; `From` converts a value it takes. None of the three names tells you whether the heap is touched — that depends on the impl a call lands on — so this page reads it off the addresses.

## The three signatures

```rust
pub trait Clone: Sized {
    fn clone(&self) -> Self;
}

pub trait ToOwned {
    type Owned: Borrow<Self>;
    fn to_owned(&self) -> Self::Owned;
}

pub trait From<T>: Sized {
    fn from(value: T) -> Self;
}
```

| | `Clone` | `ToOwned` | `From<T>` (and `Into`) |
|---|---|---|---|
| **takes** | `&Self` — the original stays | `&Self` — the original stays | `T` by value — the original is moved in |
| **gives** | `Self`, always | `Self::Owned`: `Self` for every `Clone` type ([step 6](../the_blanket_to_owned/README.md)), another type for `str`, `[T]`, `Path` … ([step 1](../clone_vs_to_owned/README.md)) | `Self`, usually another type |
| **may `Self` be unsized?** | no — `Clone: Sized` ([step 4](../clone_returns_self/README.md)) | yes ([step 2](../types_with_no_size/README.md)) | no — `From<T>: Sized` |
| **you implement it by** | `#[derive(Clone)]` | almost never ([step 10](../implementing_it_or_not/README.md)) | writing `From`, never `Into` |
| **the promise** | same type, independent value | the owned form can lend the borrowed one back ([step 8](../borrow_the_way_back/README.md)) | a conversion that cannot fail — `TryFrom` when it can |

## What each call does to the heap, measured

```text
Clone: &T -> T, always the same type
   s.clone()             &String -> alloc::string::String    new buffer: true
   n.clone()             &i32    -> i32                      no heap to copy

ToOwned: &B -> B::Owned, the same type or another one
   literal.to_owned()    &str    -> alloc::string::String    new buffer: true
   n.to_owned()          &i32    -> i32                      no heap to copy
   rc.to_owned()         &Rc     -> Rc<String>, the same one text copied: false, strong count: 2

From / Into: T -> U, and the T is gone afterwards
   String::from(literal) &str    -> alloc::string::String    new buffer: true
   Vec::from(text)       String  -> alloc::vec::Vec<u8>      new buffer: false
   again.into()          String  -> alloc::rc::Rc<str>       new buffer: true   (the counts need room)
```

Reading it row by row:

- **`Clone`** copied the `String`'s bytes into a new buffer, and had no heap to copy for an `i32`. The cost is whatever the type's `clone` does — [What a clone costs](../../../18_Ownership/what_a_clone_costs/README.md) adds it up field by field.
- **`ToOwned`** allocated for the `&str`, copied an `i32` with no heap involved, and on an `Rc` copied **no** text at all — it bumped the count ([step 7](../to_owned_traps/README.md)). So *"`ToOwned` almost always allocates"* is the wrong rule. It allocates exactly when the impl it lands on does: `str`'s does, the blanket impl's does whatever `clone` does.
- **`From`** allocated for `String::from(&str)` — a borrowed source cannot be moved, so the bytes are copied. `Vec::from(String)` reused the `String`'s buffer — same address. And `Rc<str>::from(String)` *consumed* its `String` and still allocated, because an `Rc` keeps its counts in front of the data. So *"`From` is a zero-cost move"* is true of some impls, not of the trait.

## Which one to write

- **You have a `&T` and want another `T`:** `clone()`.
- **You have a borrow and want to own it, possibly as another type:** `to_owned()`. In generic code over a borrowed type — `B: ToOwned + ?Sized`, the bound on `Cow` — it is the only one of the three that works for `str`.
- **You are converting one type into another, especially one you can give up:** implement `From`, and let callers write `.into()`. [`From` and `Into`](../../../29_Conversion/from_and_into/README.md#which-one-goes-in-a-signature) has the table of which goes in a signature.
- **A function that will store a `String`:** `name: impl Into<String>` lets a caller who already owns a `String` hand it over without a copy, while a `&str` caller still pays one allocation. The cost is one compiled copy of the function per argument type. A `&str` parameter plus `.to_owned()` inside always allocates — [one parameter serves every caller](../../../14_Strings/string_vs_str/README.md#one-parameter-serves-every-caller) weighs the two.
- **Text, specifically:** `to_owned()`, `to_string()`, `String::from` and `.into()` on a `&str` produce the same `String` for the same cost on this toolchain — [so which one — `to_string()` or `to_owned()`?](../../../14_Strings/making_a_string/README.md#so-which-one-to_string-or-to_owned) and [`ToOwned` — for everything else, they are the same call](../../to_owned/README.md#for-everything-else-they-are-the-same-call) have the measurements, and the 2016 change that made the old advice obsolete.

## Po polsku

`Clone` robi z `&T` kolejne `T`. `ToOwned` robi z pożyczki wartość posiadaną, być może innego typu. `From` zamienia wartość, którą **zabiera** (oryginał jest przeniesiony). Żadna z tych nazw nie mówi, czy powstanie alokacja — to zależy od implementacji, w którą trafi wywołanie.

Pomiar na tej stronie obala dwa popularne zdania. „`ToOwned` prawie zawsze alokuje” — nie: `42_i32.to_owned()` nie dotyka sterty, a `to_owned()` na `Rc` tylko zwiększa licznik. „`From` to przeniesienie bez kosztu” — tylko czasem: `Vec::from(String)` używa tego samego bufora, ale `Rc<str>::from(String)` alokuje, bo `Rc` potrzebuje miejsca na liczniki.
