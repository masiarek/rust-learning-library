# Packages and crates

**Level:** 101 · for newcomers

**One line:** A **package** is a folder with a `Cargo.toml`; a **crate** is one unit rustc compiles — a library or a binary — and a package holds at most one library crate and any number of binary crates, each with its own module tree rooted at one file. Every binary sees the library by the package's name and the other binaries not at all.

| Word | Lives in | Named by |
|---|---|---|
| package | `Cargo.toml` and the folder around it | `name = "…"` in the manifest |
| library crate | `src/lib.rs`, the crate root | the package's name, `-` turned into `_` |
| binary crate | `src/main.rs`, or one file each under `src/bin/` | `src/main.rs` takes the package's name; a file under `src/bin/` takes its own |
| module | `mod name;` or `mod name { … }` inside a crate | the `mod` line — see [Modules and visibility](../modules_and_visibility/README.md) |

One package with all three kinds of target:

## The library's name has an underscore

The package is `pg-pkg-two-crates`. The library crate is `pg_pkg_two_crates`, because a crate name is a Rust identifier and `-` is not allowed in one, so `use pg_pkg_two_crates::hello;` is what `main.rs` and `report.rs` write. Section 1 of the key shows both spellings side by side: the `lib` target is named with the underscore, the `bin` target that `main.rs` makes keeps the dash, since an executable's file name can hold one.

## Paths inside a crate, and the name from outside

Inside a crate every path starts from one of three places: `crate::` for the root, `self::` for the current module, `super::` for its parent. `main.rs` and `lib.rs` are two crates, so `crate::` in `main.rs` is `main.rs` — the library is reached by its name, `pg_pkg_two_crates::hello`, the way any dependency is. The kata at the end of this page walks five places in one package and says where `crate::` points from each; [One module per file](../one_module_per_file/README.md#the-crate-root) has the same fact from the module side.

## What `rustc file.rs` makes

One crate and no package. `rustc --print crate-name` on `src/main.rs` answers `main`, and on `src/bin/my_binary.rs` it answers `my_binary` — section 5 of the key — because without Cargo the crate is named after the file, and `CARGO_PKG_NAME` is not set at all. That is how every example in this library is compiled, and [Running a scratch program](../../15_First_Programs/rustc_without_cargo/README.md) is the page for it.

## The trap: shared code in `main.rs`

Each file under `src/bin/` is a crate of its own, so a module declared in `main.rs` does not exist for it:

<!-- file:demo/bin_sees_no_main/src/main.rs -->
```rust title="demo/bin_sees_no_main/src/main.rs"
//! Shared code put in main.rs, where the other binary cannot see it.

mod shared {
    pub fn greeting() -> &'static str {
        "hello"
    }
}

fn main() {
    println!("{}", shared::greeting());
}
```
<!-- /file -->

<!-- file:demo/bin_sees_no_main/src/bin/other.rs -->
```rust title="demo/bin_sees_no_main/src/bin/other.rs"
//! `crate::` here is other.rs, a crate with no `shared` module in it.

fn main() {
    println!("{}", crate::shared::greeting());
}
```
<!-- /file -->

`crate` in `other.rs` is `other.rs`. Naming the package instead, `use pg_pkg_bin_sees_no_main::shared;`, fails the same way, since there is no library crate for that name to mean — rustc even suggests `cargo add`-ing your own package. The fix is `src/lib.rs`: put `shared` there, and `main.rs` and `other.rs` both `use` it by the package's name.

## The book's `bin/` folder, and what `cargo new` writes today

*Rust: The Practical Guide* (Nouman Azam, Rheinwerk 2025) draws its package as `Cargo.toml`, `src/main.rs` and a `bin/my_binary.rs` beside `src/`, and its manifest says `edition = "2021"`. Sections 2 to 4 of the key measure both on this toolchain. `cargo new` on rustc 1.98.0 writes `edition = "2024"`. A `bin/` folder at the package root is not a target: with the book's tree, `cargo metadata` lists the one binary `main.rs` makes, the file in `bin/` is never compiled, and `cargo run` prints `Hello, world!` as if it were not there. Moved to `src/bin/`, the file becomes a second binary target, and from then on `cargo run` needs `--bin` or a `default-run` line. The rest of that chapter is checked on [What *Rust: The Practical Guide* says about packages, crates and modules, run](../modules_claims_checked/README.md).

## What crates.io calls a crate

crates.io publishes packages and calls them crates, and the docs.rs page for `serde` is one crate's documentation because that package has exactly one library. The loose usage is harmless until a package has a library and two binaries, as this page's does: then "the crate" is three things, `cargo build` makes all three, and `cargo run` asks which one you meant. [Publishing a crate](../../05_Tooling/publishing_a_crate/README.md) is where the word is used in the loose sense on purpose.

## If you are coming from another language

- **Python.** A distribution (what `pip` installs, named in [`pyproject.toml` ↗](https://masiarek.github.io/python-learning-library/02_Projects_and_Environments/pyproject_toml/)) contains import packages and modules; Rust's package → crate → module is the same three levels, with the crate as a compilation unit Python does not have. The underscore rule is Python's too: the distribution `scikit-learn` is imported as `sklearn`, and `typing-extensions` as `typing_extensions`, because an import name has to be an identifier.
- **Go.** A Go module (`go.mod`) holds packages, and a package is one directory; Rust's module tree is inside the crate rather than one per directory, and a Go `main` package is the nearest thing to a binary crate.
- **Java.** A Maven artifact is the package, a JAR is roughly the crate, and Java packages are the module tree. A JAR can hold several `main` classes and you pick one at run time; a Rust package builds one executable per binary crate and you pick at build time.
- **C and C++.** No standard unit above the translation unit: a static library, a shared library or an executable is what a crate compiles into, and what a [Makefile ↗](https://masiarek.github.io/c-learning-library/01_Building/makefiles/) lists by hand is what `cargo metadata` discovers from the file layout.

## Po polsku

Pakiet (*package*) to katalog z `Cargo.toml`; skrzynia (*crate*) to jedna jednostka kompilacji — biblioteka albo program wykonywalny. Pakiet ma najwyżej jedną skrzynię biblioteczną (`src/lib.rs`) i dowolnie wiele binarnych (`src/main.rs` i po jednym pliku w `src/bin/`); każda ma własne drzewo modułów, dlatego plik w `src/bin/` nie widzi modułów z `main.rs` (`E0433`, „could not find `shared` in the crate root”), a wspólny kod trafia do `lib.rs`, którego każdy program w pakiecie używa po nazwie pakietu. Nazwa biblioteki zamienia myślnik na podkreślenie, bo nazwa skrzyni musi być identyfikatorem: pakiet `pg-pkg-two-crates` to w kodzie `pg_pkg_two_crates`. `cargo metadata` wypisuje cele (*targets*), które Cargo naprawdę znajdzie — i pokazuje, że katalog `bin/` obok `src/` nie jest żadnym z nich; na rustc 1.98.0 `cargo new` wpisuje do manifestu `edition = "2024"`.
