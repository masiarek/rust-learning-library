# Decimals: `rust_decimal`, `bigdecimal` and Python's `Decimal`

[Other number types](../README.md) › **Decimals**

**Level:** 201 · working knowledge

**One line:** In a base-10 type, `0.1 + 0.2 == 0.3` is true. Python ships one, `decimal.Decimal`. Rust's answers are an integer count of cents or a crate that is not `num`: `rust_decimal` keeps about 28 digits, like Python's default, but it overflows where Python rounds and builds `0.1` from a float differently. For more digits than that, use `bigdecimal` or `dashu-float`.

## With std only: count whole cents

<!-- source:cents_are_exact -->
*[`cents_are_exact.rs`](examples/cents_are_exact.rs) in full — pasted here by `tools/run_examples.py` from the file CI compiles and runs.*

```rust
// Three items at $0.10: as a float, and as whole cents.
fn main() {
    let total = 0.10_f64 * 3.0;
    println!("{total}"); // 0.30000000000000004
    println!("{}", total == 0.30); // false

    let total_cents: i64 = 10 * 3;
    println!("{}.{:02}", total_cents / 100, total_cents % 100); // 0.30
    println!("{}", total_cents == 30); // true

    // What whole cents cannot do: split a dollar three ways.
    println!("{} cents each, {} left over", 100 / 3, 100 % 3); // 33 cents each, 1 left over
}
```

`0.10` is not exactly representable as an `f64` ([why](../../what_a_float_stores/README.md)), so three of them sum to `0.30000000000000004`. Ten cents is exactly `10`. An integer count of the smallest unit is exact under `+`, `−` and `×`, needs no crate, and is `Copy`, `Eq`, `Ord` and `Hash`. Where it stops is division, as the last line shows: a third of a dollar has no whole number of cents, so the program has to decide who gets the leftover cent. [Scale the denominator away](../../../09_Advanced/scaled_integers/README.md) takes that idea as far as it goes.

## `rust_decimal` and `Decimal`, side by side

```rust title="src/main.rs — cargo 1.98.0, rust_decimal 1.43.0, rust_decimal_macros 1.40.0"
use rust_decimal::Decimal;
use rust_decimal_macros::dec;

fn main() {
    println!("{}", dec!(0.1) + dec!(0.2) == dec!(0.3));   // true
    println!("{}", dec!(1.50) + dec!(1.50));              // 3.00
    println!("{}", dec!(1) / dec!(3));                    // 0.3333333333333333333333333333
    println!("{}", dec!(1000000) / dec!(3));              // 333333.33333333333333333333333
    println!("{}", dec!(2.5).round());                    // 2
    println!("{:?}", Decimal::try_from(0.1_f64));         // Ok(0.1)
    println!("{:?}", Decimal::MAX.checked_add(dec!(1)));  // None
}
```

```python title="Python 3.14.7"
from decimal import Decimal

print(Decimal('0.1') + Decimal('0.2') == Decimal('0.3'))  # True
print(Decimal('1.50') + Decimal('1.50'))                  # 3.00
print(Decimal(1) / Decimal(3))                            # 0.3333333333333333333333333333
print(Decimal(1000000) / Decimal(3))                      # 333333.3333333333333333333333
print(round(Decimal('2.5')))                              # 2
print(Decimal(0.1))                                       # 0.1000000000000000055511151231257827021181583404541015625
print(Decimal('79228162514264337593543950335') + 1)       # 7.922816251426433759354395034E+28
```

`dec!` is a macro from the separate `rust_decimal_macros` crate. It reads the literal's digits at compile time, so `dec!(0.1)` never passes through an `f64`: `dec!(0.1000000000000000000001)` prints all 22 decimal places, more than an `f64` can hold. Python's equivalent is the string: `Decimal('0.1')`.

Four lines agree: `0.3` is `0.3`, `1.50 + 1.50` keeps its trailing zero as `3.00` in both, `1/3` is 28 threes in both, and `round` sends the tie `2.5` to the even `2` in both. Three lines disagree:

| | Python `Decimal` | `rust_decimal::Decimal` |
|---|---|---|
| What limits the digits | the context: 28 **significant digits** by default, and you can change it | the type: a **96-bit integer** and a scale from 0 to 28, in 16 bytes |
| 1000000 / 3 | `333333.3333333333333333333333` — 28 significant digits | `333333.33333333333333333333333` — 29, as many as fit in 96 bits |
| One past the largest value | rounds to `7.922816251426433759354395034E+28` and sets the `Inexact` and `Rounded` flags, with no exception | `checked_add` returns `None`, and a plain `+` panics with `Addition overflowed` |
| Built from the float `0.1` | `Decimal(0.1)` keeps every digit the float stores: 55 of them | `Decimal::try_from(0.1_f64)` gives `0.1`, and `Decimal::from_f64_retain(0.1_f64)` gives `0.1000000000000000055511151231` |

The last row is a trap in both directions. Python's `Decimal(0.1)` shows you the float's error exactly, which surprises people who expected `0.1`. `rust_decimal`'s `try_from` rounds the error away, which hides that the float was wrong to begin with. Neither is a way to get a decimal: start from a string or `dec!`.

`Decimal::MAX` is `79228162514264337593543950335`, which is 2⁹⁶ − 1. The type is `Copy`, like an integer.

**Neither is fixed-point.** The scale belongs to each value, not to the type: `dec!(1.50) * dec!(1.50)` is `2.2500`, scale 4, in both languages. If every amount must have exactly two decimal places, round to two after each multiplication or division (`round_dp(2)` in `rust_decimal`, `quantize(Decimal('0.01'))` in Python). Both default to rounding a tie to even: `1.005` becomes `1.00`. Python gives `1.01` if you pass `rounding=ROUND_HALF_UP`.

## When 28 digits is not enough

`rust_decimal` has a fixed size. For a number of digits you choose at run time, like Python's `getcontext().prec`, there are two pure-Rust crates:

```rust title="src/main.rs — cargo 1.98.0, bigdecimal 0.4.10, dashu-float 0.6.0"
use bigdecimal::BigDecimal;
use dashu_float::DBig;

fn main() {
    println!("{}", BigDecimal::from(2).sqrt().unwrap().with_prec(50));  // 1.4142135623730950488016887242096980785696718753769
    println!("{}", DBig::from(2u8).with_precision(50).value().sqrt());  // 1.4142135623730950488016887242096980785696718753769
}
```

```python title="Python 3.14.7"
from decimal import Decimal, getcontext

getcontext().prec = 50
print(Decimal(2).sqrt())  # 1.4142135623730950488016887242096980785696718753769
```

All three give the same 50 significant digits of √2. The Rust crates take the precision per value — `with_prec(50)`, `with_precision(50)` — where Python sets it once, in a context that every later operation reads. That makes a Python function's result depend on a context its caller may have changed. Division in `bigdecimal` defaults to 100 digits: `BigDecimal::from(1) / BigDecimal::from(3)` prints 100 threes. The third option is `rug`, which wraps the C libraries GMP and MPFR, so building it needs a C toolchain.

## Which one

- **Whole cents in an `i64`**, when amounts only add, subtract and multiply by whole numbers. It needs no crate, and sorting, hashing and `==` work as on any integer.
- **`rust_decimal`** for money that needs division or rates. It is `Copy` and never allocates. Use `checked_*` arithmetic where an overflow must not panic.
- **`bigdecimal` or `dashu-float`** when you need a set number of digits beyond 28, as in scientific or test-oracle code. The cost is a heap allocation per value.
- **`f64`** for measurements, where the input was never exact. [What a float actually stores](../../what_a_float_stores/README.md) covers what that costs.

## If you are coming from Python

**What transfers:** almost everything you know about `Decimal` holds for `rust_decimal`. Build from strings, not floats. Trailing zeros are kept and compare equal (`1.10 == 1.1` is true in both). Ties round to even. And a third has no exact decimal, so any division rounds somewhere.

**What changes:**

- **No context.** Python's precision, rounding mode and traps live in a thread-local context that `localcontext()` can change. `rust_decimal` has none. The limits are the type's, and the rounding mode is an argument: `round_dp_with_strategy(2, RoundingStrategy::MidpointAwayFromZero)`.
- **Overflow is an error, not a rounding.** Python's `Decimal` quietly loses digits at the top and records it in a flag you have to look at. `rust_decimal` panics on `+`, or returns `None` from `checked_add`.
- **Floats are refused by `+`, in both.** `Decimal('0.1') + 0.1` raises `TypeError`. In Rust, `dec!(0.1) + 0.1` is `E0277`: *cannot add `{float}` to `Decimal`*. Converting has to be written out, and as the table shows, the two languages convert differently.
- **Not in std.** Python's `decimal` comes with the interpreter. In Rust it is a dependency with a version, chosen from several crates with different trade-offs.

## Po polsku

Liczba dziesiętna (*decimal*) liczy w podstawie 10, więc `0.1 + 0.2 == 0.3` jest prawdą. Python ma ją w standardzie (`decimal.Decimal`). W Ruscie są dwie drogi. Pierwsza: trzymać grosze (*cents*) w `i64` — dokładnie, bez crate'a, ale bez dzielenia. Druga: crate `rust_decimal` — nie `num`, bo `num` liczb dziesiętnych nie ma.

`rust_decimal` i Pythonowy `Decimal` zachowują się podobnie (zera na końcu, zaokrąglanie do parzystej, około 28 cyfr), ale różnią się w trzech miejscach. Granica: w Pythonie to 28 cyfr znaczących z kontekstu, który można zmienić; w Ruscie 96-bitowa liczba całkowita, czyli do 29 cyfr. Przepełnienie: Python po cichu zaokrągla i ustawia flagę, `rust_decimal` panikuje albo zwraca `None`. Konwersja z `f64`: `Decimal(0.1)` pokazuje wszystkie 55 cyfr błędu, a `Decimal::try_from(0.1)` w Ruscie ten błąd zaokrągla. I jeszcze jedno: żadne z nich nie jest stałoprzecinkowe (*fixed-point*) — skala należy do wartości, nie do typu. Gdy 28 cyfr to za mało, jest `bigdecimal` albo `dashu-float`.
