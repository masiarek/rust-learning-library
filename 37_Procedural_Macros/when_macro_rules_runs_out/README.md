# When `macro_rules!` runs out

**Level:** 301 · deep dive

**One line:** `macro_rules!` can count its arguments, check a string literal through a `const`, and word its own errors; what it cannot do on stable Rust is write an identifier that is not in its input — `incr_requests` from `requests` — and that is where a function-like procedural macro starts to pay for its extra crate.

## The task, done by a procedural macro

`counters!(requests, errors)` should define a struct with a `u64` per name, and a method `incr_<name>` for each:

<!-- file:demo/counters_app/src/main.rs -->
```rust title="demo/counters_app/src/main.rs"
counters_macro::counters!(requests, errors);

fn main() {
    let mut counts = Counters::new();
    counts.incr_requests();
    counts.incr_requests();
    counts.incr_errors();
    println!("requests = {}, errors = {}", counts.requests, counts.errors); // requests = 2, errors = 1
}
```

The macro parses a comma-separated list of identifiers and builds one new identifier per name with `format_ident!`:

<!-- file:demo/counters_macro/src/lib.rs -->
```rust title="demo/counters_macro/src/lib.rs"
//! `counters!(requests, errors)`: a struct with one `u64` per name, and an
//! `incr_<name>` method for each.

use proc_macro::TokenStream;
use quote::{format_ident, quote};
use syn::punctuated::Punctuated;
use syn::{Ident, Token, parse_macro_input};

#[proc_macro]
pub fn counters(input: TokenStream) -> TokenStream {
    let names = parse_macro_input!(input with Punctuated::<Ident, Token![,]>::parse_terminated);
    let fields: Vec<&Ident> = names.iter().collect();
    // The identifier `macro_rules!` cannot write. `format_ident!` gives it the
    // span of `name`, the name as the caller typed it.
    let methods: Vec<Ident> = fields.iter().map(|name| format_ident!("incr_{}", name)).collect();
    quote! {
        pub struct Counters {
            #(pub #fields: u64,)*
        }

        impl Counters {
            pub fn new() -> Self {
                Self { #(#fields: 0,)* }
            }

            #(pub fn #methods(&mut self) {
                self.#fields += 1;
            })*
        }
    }
    .into()
}
```

## The same task in `macro_rules!`

Everything except the method names translates line for line:

<!-- file:demo/rules_pasted/src/main.rs -->
```rust title="demo/rules_pasted/src/main.rs"
//! `counters!` as a `macro_rules!` macro. The struct and its fields expand
//! fine; the method names do not.

macro_rules! counters {
    ($($name:ident),* $(,)?) => {
        pub struct Counters {
            $(pub $name: u64,)*
        }

        impl Counters {
            pub fn new() -> Self {
                Self { $($name: 0,)* }
            }

            $(pub fn incr_$name(&mut self) {
                self.$name += 1;
            })*
        }
    };
}

counters!(requests, errors);

fn main() {
    let mut counts = Counters::new();
    counts.incr_requests();
    println!("requests = {}", counts.requests);
}
```

`incr_$name` is not one identifier with a hole in it. The lexer read `incr_` as a complete identifier when the macro was defined, and `$name` substitutes a second, whole token after it, so the parser sees `fn incr_ requests(…)`: a function called `incr_`, with something that is not a parameter list after the name. The *help* is the parser's guess at that reading, not a fix. `macro_rules!` substitutes tokens; it never joins two into one. The third error follows from the first two: no `incr_requests` was defined, so `main` cannot call it.

The feature that does join them exists, and it is not stable:

Only the method line changed, to `pub fn ${concat(incr_, $name)}(&mut self)`. `${concat(…)}` is a *metavariable expression*, and in 1.98.0 it is behind a feature gate. It replaced the older `concat_idents!`, which std lists as removed since 1.90.0 ([`std/src/lib.rs` at 1.98.0 ↗](https://github.com/rust-lang/rust/blob/1.98.0/library/std/src/lib.rs#L441-L446)).

This is the exact point where `macro_rules!` stops. On stable, a name that is not already a token in the input can only come from a procedural macro. The crate people reach for is [`paste` ↗](https://docs.rs/crate/paste/1.0.15/source/src/lib.rs#164), a `#[proc_macro]` whose documentation shows it used from *inside* a `macro_rules!` macro, pasting `[<get_ $field>]` into one identifier.

## What `macro_rules!` can still do

The pull toward a procedural macro often starts earlier than it has to. None of these needs one:

<!-- file:demo/still_rules/src/lib.rs -->
```rust title="demo/still_rules/src/lib.rs"
//! Three jobs that sound like they need a procedural macro, done with
//! `macro_rules!` and a `const fn`.

/// Counts its arguments without recursion: one `()` per name, in a slice
/// whose length is a constant.
#[macro_export]
macro_rules! count {
    ($($name:ident),* $(,)?) => {
        <[()]>::len(&[$($crate::count!(@unit $name)),*])
    };
    (@unit $name:ident) => {
        ()
    };
}

/// Checks a string literal's contents while compiling. The macro cannot look
/// inside the literal, but a `const` it expands to can.
#[macro_export]
macro_rules! hex {
    ($text:literal) => {{
        const _: () = assert!($crate::all_hex($text), "not a hex string");
        $text
    }};
}

/// An error message of the macro's own, naming the token it refused.
#[macro_export]
macro_rules! method {
    (GET) => {
        "GET"
    };
    (POST) => {
        "POST"
    };
    ($other:ident) => {
        compile_error!(concat!("unknown method `", stringify!($other), "`"))
    };
}

pub const fn all_hex(text: &str) -> bool {
    let bytes = text.as_bytes();
    let mut i = 0;
    while i < bytes.len() {
        if !bytes[i].is_ascii_hexdigit() {
            return false;
        }
        i += 1;
    }
    true
}
```

- **Counting.** `count!` expands to a slice with one `()` per name and takes its length. No recursion over the list, and the result is a constant: `count!(requests, errors)` sizes an array. So the claim that `macro_rules!` can only count by recursing is wrong.
- **Checking a literal's contents.** The macro cannot see inside `"c0ffee"`: to a matcher, a `literal` is one token. It can hand the literal to a `const fn`, and a failing `assert!` in a `const` stops compilation.
- **An error of its own.** `compile_error!` takes a message built with `concat!` and `stringify!`, so the message can name the token it refused.

Both messages the macro wrote underline the **whole call**, `hex!("coffee")` and `method!(PATCH)`, never the literal or the identifier inside it. The one precise underline is the compiler's own: when no rule matches, `no rules expected` points at the token, here `"GET"` written as a string. A procedural macro puts a `syn::Error` on any token it likes, which is what [A `routes!` macro](../a_routes_macro/README.md) does with a `{param}` its handler does not take.

## The decision, for a function-like macro

| You need | `macro_rules!` | A `#[proc_macro]` |
|---|---|---|
| Syntax a function cannot take: any number of arguments, names, types | Yes | Yes |
| A count of the arguments | Yes, as a constant: `<[()]>::len(&[…])` | Yes |
| A new identifier such as `incr_requests` | **No** on stable: tokens are never joined, `${concat(…)}` is unstable | Yes: `format_ident!` |
| To reject a string literal by its contents | Yes, through a `const fn`; the error underlines the whole call | Yes; the error underlines the literal |
| To turn a literal's contents into code: a pattern, a parameter | **No**: a matcher cannot see inside a literal | Yes: [A `routes!` macro](../a_routes_macro/README.md) |
| A message of its own | Yes, `compile_error!`; underlines the whole call | Yes, `syn::Error`; underlines any token |
| To live in the crate that uses it | Yes | No: a crate of its own, `proc-macro = true` |
| Dependencies to compile first | None | `syn`, `quote`, `proc-macro2`, `unicode-ident` |

Start with `macro_rules!`. Move when a row in bold is the one you need, or when the error your users see has to point somewhere more exact than the whole call.

## If you are coming from another language

- **C and C++.** The preprocessor can do the one thing on this page `macro_rules!` cannot: `##` pastes two tokens into one, so `#define COUNTER(name) static unsigned long name; static void incr_##name(void) { name += 1; }` defines `incr_requests` (checked with Apple clang 21: `clang -E` prints `static void incr_requests(void)`). It cannot look inside a string literal, and it pastes text without knowing what the text is. Rust's split is the other way round: `macro_rules!` matches structured fragments and will not paste, and pasting is a job for a procedural macro.
- **Python.** Methods named at run time are ordinary: `setattr(Counters, f"incr_{name}", incr)` in a loop builds `incr_requests` while the module runs. The price is that a misspelt call, `c.incr_retries()`, is an `AttributeError` when that line runs (Python 3.14 even suggests `incr_errors`). The Rust version builds the method while compiling, so the same typo is a compile error.
- **Java.** No macros. An annotation processor or Lombok builds `getName` from `name` as a string and emits source or bytecode; that is the procedural macro's position, a program generating names, and it runs inside `javac` the way a procedural macro runs inside `rustc`.
- **ABAP.** *(Not machine-checked — CI cannot run ABAP.)* `DEFINE` macros substitute placeholders, and a name built at run time is a dynamic call, `CALL METHOD (lv_name)`, checked only when it runs. A method generated with a new name at compile time has no ABAP counterpart outside code generators.

## Po polsku

`macro_rules!` potrafi więcej, niż się zwykle mówi. **Policzy argumenty** bez rekurencji (`<[()]>::len(&[…])` daje stałą, którą można wpisać jako długość tablicy), **sprawdzi zawartość literału** przez `const fn` i `assert!` w bloku `const`, a przez `compile_error!` zgłosi **własny komunikat błędu**. Podkreślenie obejmuje wtedy jednak całe wywołanie makra, a nie token, który był zły.

Czego nie zrobi na stabilnym Ruście: nie **zbuduje nowego identyfikatora**. `incr_$name` to dwa tokeny, `incr_` i podstawione `requests`, bo makro deklaratywne podstawia całe tokeny i nigdy ich nie skleja. Wyrażenie `${concat(incr_, $name)}` robi dokładnie to, ale w 1.98.0 jest niestabilne (E0658), a starsze `concat_idents!` usunięto w 1.90.0. W tym miejscu opłaca się **makro proceduralne funkcyjne**: `format_ident!("incr_{}", name)` z `quote`. Kosztuje osobny crate i zależności `syn`, `quote`, `proc-macro2`, więc zaczynaj od `macro_rules!`, a przechodź dopiero wtedy, gdy potrzebujesz nowej nazwy, kodu zbudowanego z treści literału albo błędu wskazującego dokładny token.
