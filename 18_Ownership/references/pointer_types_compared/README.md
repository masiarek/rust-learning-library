# Six pointer types, one table

[References](../README.md) › **Six pointer types, one table**

**Level:** 201 · working knowledge

**One line:** `&T`, `&mut T`, `*const T`, `*mut T`, `Box<T>` and `Rc<T>` differ on seven questions — who drops the pointee, what a write needs, `Copy`, `unsafe`, null, size, and where the pointee may be — and the popular table of them fills in columns it never defines.

```rust
use std::rc::Rc;

fn main() {
    let mut n = 1;

    let shared: &i32 = &n;               // borrows n
    println!("{shared}");                // 1

    let exclusive: &mut i32 = &mut n;    // borrows n, and nothing else may
    *exclusive += 1;

    let raw: *mut i32 = &mut n;          // no borrow the compiler tracks
    unsafe { *raw += 1 };                // so every use is unsafe
    println!("{n}");                     // 3

    let boxed: Box<i32> = Box::new(n);   // copies 3 into an allocation it owns
    let counted: Rc<i32> = Rc::new(n);   // the same, plus a count of owners
    let second = Rc::clone(&counted);    // a second owner, not a second 3
    println!("{boxed} {second} {}", Rc::strong_count(&counted)); // 3 3 2
}
```

Two of these borrow `n`, one points at it untracked, and two own a copy of it. That split — borrow, point, own — decides most of the table.

What each row asks, where the name alone does not say:

- **owns (drops) pointee** — ending the pointer's scope runs the pointee's destructor. The program counts the runs.
- **write through it** — `*p = v` compiles and lands. *if mut* is the binding: `let mut b = Box::new(1)`, as for any owned value, while a `&mut T` binding needs no `mut` (`*exclusive += 1` above). *if unique* is [`Rc::get_mut` ↗](https://doc.rust-lang.org/std/rc/struct.Rc.html#method.get_mut), which returns `Some` only while the count is 1.
- **Copy** — `Probe<T>` has an inherent `is_copy` in an `impl<T: Copy>` block and a same-named trait method returning `false`. Method lookup takes the inherent one only when the bound holds, so the call answers the question for a concrete type; the controls line shows it saying `true` for `i32` and `false` for `String`. The three yeses are also compiled through a `fn assert_copy<T: Copy>()`.
- **can be null** — *yes* where `Option<P>` needs a word of its own. A pointer that is never null lends `None` the null bit pattern; [`Option`'s docs ↗](https://doc.rust-lang.org/std/option/index.html#representation) guarantee this for `&T`, `&mut T` and `Box<T>` with a sized `T`; for `Rc<T>` it is measured, not promised.
- **pointee may live** — *anywhere* is one type, `&i32`, pointed at a local, a `static` and the inside of a `Box`. A raw pointer may also point nowhere (`ptr::null()`). *heap* for `Box` and `Rc` is what their std docs state; for `Box`, [only for a non-zero-sized `T` ↗](https://doc.rust-lang.org/std/boxed/index.html#memory-layout).
- **words** — the handle's own size. Every one of the six grows to two words for `[u8]`, `str` and `dyn Display`, for the reason [`str` is unsized](../../../14_Strings/str_is_unsized/README.md) gives.

## What the popular table gets wrong

The second-highest answer on Stack Overflow's *Understanding and relationship between Box, ref, & and \** (Mohamad-Jaafar Nehme, October 2022, edited June 2023) tabulates the same six types under *Data Location*, *Mutable*, *Shared Ownership*, *Safe* and *impl Copy*. Its `impl Copy` column matches the table above, and so does *Safe*, read the way its own note defines it (dereferencing needs `unsafe`). The rest:

- **Data Location: "stack" for `&T`, `&mut T`, `*const T`, `*mut T`.** That is where a pointer *variable* often sits, and says nothing about the pointee — and the variable is not always there either. Section 1 of the verified output below: `let r: &i32 = &*boxed;` points into the `Box`'s allocation (`ptr::eq` is `true`); a `Vec<&str>` keeps its references as elements of its buffer, which [`Vec`'s docs ↗](https://doc.rust-lang.org/std/vec/struct.Vec.html#guarantees) place on the heap; `Box<&i32>` is a reference on the heap pointing at a local. The row worth having is where the pointee may live.
- **Shared Ownership ✓ for `&T`, `*const T` and `*mut T`.** None of them owns anything: ending each one's scope ran 0 destructors. Many `&T` can share *access* to a value; its one owner is still the binding they borrowed from.
- **`&mut T` ✗, because it "has only one owner".** The refusal it cites, `E0499` *"cannot borrow `x` as mutable more than once at a time"*, is about two live exclusive borrows of `x` — and `x` is the owner throughout. A `&mut T` ran 0 destructors too. Exclusive access, not ownership.
- **`Box<T>` ✗, shown by an `E0597`.** The example it links borrows `b = Box::new(1)` in an inner block and uses the borrow after the block. Change `Box::new(1)` to `1` and rustc prints the same error — same code, same message, same four labels:

  ```text title="Abridged — real rustc output for borrow_outlives_int.rs"
  error[E0597]: `b` does not live long enough
   --> borrow_outlives_int.rs:5:17
    |
  4 |         let b = 1;
    |             - binding `b` declared here
  5 |         b_ref = &b;
    |                 ^^ borrowed value does not live long enough
  6 |     }
    |     - `b` dropped here while still borrowed
  7 |     println!("{}", b_ref);
    |                    ----- borrow later used here
  ```

  `E0597` is a borrow outliving whatever it borrowed. A `Box` has one owner, but the evidence for that is the drop count — one `Box` in scope, one destructor run — not this error.
- **`Rc<T>` Mutable ✗, shown by an `E0594`.** The refusal's own `help:` line names what is missing, `DerefMut`, and std writes through an `Rc` another way: `Rc::get_mut` while the count is 1, and [`Rc::make_mut` ↗](https://doc.rust-lang.org/std/rc/struct.Rc.html#method.make_mut), which clones the value first when it is shared (section 2: `a = 12`, `b = 2`, no longer the same allocation). Several owners that all write is `Rc<RefCell<T>>` — [Shared means read-only](../../reference_counting/README.md#shared-means-read-only).

## `*const T` and `*mut T` differ in more than a lint

The accepted answer on the same question (Vladimir Matveev, 2015) says the two cast into each other without restriction, so the distinction *"serves mostly as a lint"*. The casts are real — section 3 goes `*mut` → `cast_const()` → `as *mut i32` and writes through the result, no `unsafe` needed for the casts. Two things the compiler still holds you to: writing through a `*const T` is the `E0594` above, and the two have different **variance**.

```rust
fn shorten_const<'a>(p: *const &'static str) -> *const &'a str {
    p // compiles: *const T is covariant in T
}

// fn shorten_mut<'a>(p: *mut &'static str) -> *mut &'a str {
//     p // refused: *mut T is invariant in T
// }
```

```text title="Abridged — real rustc output for mut_ptr_invariant.rs"
error: lifetime may not live long enough
 --> mut_ptr_invariant.rs:6:5
  |
5 | fn shorten_mut<'a>(p: *mut &'static str) -> *mut &'a str {
  |                -- lifetime `'a` defined here
6 |     p
  |     ^ returning this value requires that `'a` must outlive `'static`
  |
  = note: requirement occurs because of a mutable pointer to `&str`
  = note: mutable pointers are invariant over their type parameter
```

A `*const T` may be handed a shorter lifetime; a `*mut T` may not, because something could be written through it that does not live long enough. The Reference's [variance table ↗](https://doc.rust-lang.org/reference/subtyping.html#r-subtyping.variance.builtin-types) lists the same, and [What `&'a T` claims](../../what_a_reference_claims/README.md) is the `&`/`&mut` version of the argument.

## `Box<T>` is neither always one pointer wide nor only a pointer

The accepted answer also describes a `Box<T>` as a `T` that always occupies one pointer's worth of bytes. The table's words rows refute it for unsized pointees: `Box<[u8]>`, `Box<str>` and `Box<dyn Display>` are two words, like every other pointer to those types. [The third owned form](../../../14_Strings/boxed_str/README.md) is the page on `Box<str>`.

And `Box` does something the other smart pointer here cannot: `*boxed` moves the value out. Section 4 moves a whole `String` out of a `Box<String>` and then two fields, one at a time, out of a `Box<Pair>`. The same line on an `Rc` is refused — the file's `Box` line, line 5, compiled:

 --> move_out_of_rc.rs:8:27

8 |     let from_rc: String = *counted;

Noratrieb's [Box Is a Unique Type ↗](https://noratrieb.dev/blog/posts/box-is-a-unique-type/) opens with that partial move and is mostly about a subtler special case: the no-aliasing promise the compiler attaches to a `Box` argument.

The accepted answer's `let y: &u32 = &*x;` borrows *through* the box: `y` points at the `u32` in the allocation, so the `Box` cannot go while `y` is still used. No lifetime is written anywhere, and the refusal comes anyway:

## `==` looks through the pointer; `ptr::eq` does not

A 2026 answer on the same question (plugwash) points out that comparing references compares what they point at. Section 5: `&five == &also_five` is `true` for two different locals holding 5, and [`std::ptr::eq` ↗](https://doc.rust-lang.org/std/ptr/fn.eq.html) on the same pair is `false`. `Box::new(5) == Box::new(5)` and `Rc::new(5) == Rc::new(5)` are `true` for the same reason. For `Rc`, the address comparison is [`Rc::ptr_eq` ↗](https://doc.rust-lang.org/std/rc/struct.Rc.html#method.ptr_eq).

## A reference is a pointer with rules

Cliffle's [*Learn Rust the Dangerous Way*, part 2 ↗](https://cliffle.com/p/dangerust/2/#what-s-a-reference) puts it this way: to the machine a reference is a pointer, and to the programmer it is a pointer that cannot be null, must point to initialized memory, and has no pointer arithmetic — checked at compile time. Three of those are visible from safe code:

- **Not null.** `Option<&i32>` is one word and `Option<*const i32>` is two (section 6, and the table's last row). [Null dereference](../../../31_C_and_Cpp/null_dereference/README.md) is the C side of that.
- **No arithmetic.** On a `*const i32` into `[10, 20, 30]`, `raw.add(1)` moves the pointer and reads `20`. On a `&i32` there is no such method:

  ```text title="Abridged — real rustc output for no_arithmetic_on_references.rs"
  error[E0599]: no method named `add` found for reference `&i32` in the current scope
   --> no_arithmetic_on_references.rs:4:18
    |
  4 |     let next = r.add(1);
    |                  ^^^ method not found in `&i32`
    |
    = help: items from traits can only be used if the trait is in scope
  help: trait `Add` which provides `add` is implemented but not in scope; perhaps you want to import it
    |
  1 + use std::ops::Add;
    |
  ```

  Take rustc's suggestion and it compiles — as integer addition. `first.add(1)` with `std::ops::Add` in scope is `11`: the pointee plus one.
- **The length is not implied.** `&[i32; 3]` is one word, because the `3` is part of the type; `&[i32]` is two, because the length has to travel with the pointer. A C pointer to the first element carries neither.

The initialized-memory rule has no safe-code demonstration: breaking it takes `unsafe`, and the result is undefined behaviour rather than an output.

## Is `Rc` a smart pointer?

Yes. The Book's [chapter 15 introduction ↗](https://doc.rust-lang.org/book/ch15-00-smart-pointers.html) calls a reference the most common kind of pointer, one that only borrows, and defines smart pointers as data structures that act like pointers while carrying extra metadata and capabilities, and in many cases owning what they point to. It lists `Rc<T>` among std's smart pointers, with `Box<T>`; an `Rc`'s extra metadata is its count.

## If you are coming from another language

- **C++.** `*const T` and `*mut T` are `const T*` and `T*`. `Box<T>` is closest to `std::unique_ptr<T>` — one owner, freed at scope end, not copyable — with two differences the table measures or rustc enforces: a `Box` is never null (`Option<Box<T>>` is one word, so "no box" is spelled `None`), and using a `Box` after moving it is `E0382` at compile time rather than a null `unique_ptr` at run time. `Box<[T]>` is two words because it carries its length, which `unique_ptr<T[]>` does not store. `Rc<T>` is `std::shared_ptr<T>` without the atomic count — Rust splits that into `Rc` and [`Arc`](../../sharing_across_threads/README.md) — and is one word for a sized `T`, where a `shared_ptr` is two pointers (libc++, measured with clang). Then the trap: `==` on two `unique_ptr`s or `shared_ptr`s compares addresses; on two `Box`es, `Rc`s or references in Rust it compares values. `std::ptr::eq` and `Rc::ptr_eq` are the C++ meaning. A Rust reference is also not a C++ reference: it is an ordinary value you can store, copy (`&T`) and re-point through a `mut` binding.
- **Python.** In CPython every name is a reference to a reference-counted object, so all of Python is roughly `Rc<T>` — without the write restriction, which is why aliasing bugs surface at run time there. `is` is `std::ptr::eq` and `==` is `==`, the same split section 5 prints. Python has no `&mut T`: nothing lets you promise that a list you passed will not be changed by someone else holding it.

## Po polsku

Sześć typów wskaźnikowych — `&T`, `&mut T`, `*const T`, `*mut T`, `Box<T>` i `Rc<T>` — różni się w siedmiu pytaniach, a każdą komórkę tabeli wyżej wypełnia albo pomiar programu, albo prawdziwa odmowa kompilatora. Pierwsze pytanie rozstrzyga najwięcej: **kto jest właścicielem**. Referencje i surowe wskaźniki niczego nie posiadają — koniec ich zasięgu nie uruchomił ani jednego destruktora. `Box` posiada wskazywaną wartość sam, `Rc` wspólnie z innymi klonami i zwalnia ją dopiero przy ostatnim.

Popularna tabela ze Stack Overflow myli pojęcia. Kolumna „położenie danych: stos” opisuje, gdzie zwykle leży *zmienna* wskaźnikowa, a nie to, na co wskazuje: `&*boxed` wskazuje na stertę, a `Vec<&str>` trzyma referencje w buforze na stercie. „Współdzielona własność” dla `&T` i surowych wskaźników to pomylenie dostępu z własnością. `&mut T` to **dostęp wyłączny**, nie jedyny właściciel. Błąd `E0597` pojawia się identycznie, gdy zamiast `Box::new(1)` pożyczymy zwykłe `1`, więc niczego nie mówi o `Box`. A `Rc` da się modyfikować, dopóki jest jedynym właścicielem: `Rc::get_mut` albo `Rc::make_mut` (to drugie najpierw klonuje wartość, jeśli jest współdzielona).

Przyjęta odpowiedź też ma dwie nieścisłości. `Box<str>`, `Box<[T]>` i `Box<dyn Trait>` zajmują **dwa słowa**, nie jedno — tak jak każdy inny wskaźnik do typu bez rozmiaru. A `*const T` i `*mut T` to nie tylko „podpowiedź”: przez `*const T` nie da się pisać (`E0594`), a wariancja jest inna — `*const T` jest kowariantny, `*mut T` niezmienniczy. Do tego `Box` jako jedyny pozwala wyprowadzić wartość przez `*boxed`; to samo na `Rc` to `E0507`. Porównanie `==` na referencjach porównuje wartości, a adresy porównuje `std::ptr::eq`. `Rc` jest inteligentnym wskaźnikiem w sensie rozdziału 15 Księgi: zachowuje się jak wskaźnik, a dodatkowo niesie licznik.
