# When the type checker is wrong

**Level:** 301 · deep dive

**One line:** *Sound* is a property of the checker, not of your code — it claims that no program rustc accepts can cause undefined behaviour, and a **soundness bug** is a counterexample: a program with no `unsafe` anywhere in it that the compiler accepts and should have rejected.

## Three different things get called sound

| Said of | Whose promise | It claims | A counterexample is |
|---|---|---|---|
| a safe API over an `unsafe` core | yours | no safe caller of this module can reach undefined behaviour | your bug — [`split_at_mut` with its `assert!` deleted](../../09_Advanced/what_unsafe_turns_off/README.md) |
| the type system | the language's design | no well-typed program can reach undefined behaviour | a proof obligation; [RustBelt ↗](https://plv.mpi-sws.org/rustbelt/popl18/) discharged it for a formal model of a core of Rust |
| **rustc's type checker** | the implementation | no program *it accepts* can reach undefined behaviour | an issue number |

The third row is this page. A design can be proved sound and still be implemented by a program with bugs in it, and the compiler on your disk is that program.

## Only one kind of compiler bug is silent

| Kind | What you see |
|---|---|
| ICE / crash | rustc panics and says so |
| miscompilation | the program was accepted correctly and the machine code is wrong — [LLVM's half of the pipeline](../llvm_and_its_ir/README.md) as readily as rustc's |
| diagnostics bug | the refusal is right, the message is bad |
| **soundness bug** | **a clean build** |

Success is the symptom, which is why these are found by people probing the type system rather than by people whose program broke.

## One you can run

`enum` variants that carry no data cast to their discriminant. A variant that carries data is a constructor *function*, and casting **that** is accepted too — giving the function's address, which looks exactly like a discriminant and is not one.

<!-- source:when_the_type_checker_is_wrong -->
*[`when_the_type_checker_is_wrong.rs`](examples/when_the_type_checker_is_wrong.rs) in full — pasted here by `tools/run_examples.py` from the file CI compiles and runs.*

```rust
// Issue 136508, rust-lang/rust: an enum constructor can be cast to an integer.
//
// This program compiles WITH A WARNING on purpose. The warning is the lesson:
// rustc 1.98.0 accepts the cast below and reports it under the lint
// `function_casts_as_integer`, which is warn-by-default.

enum Tag {
    Zero,
    One,
}

enum Wrapped {
    Value(i32),
}

fn main() {
    // A variant carrying no data casts to its discriminant: a compile-time
    // constant, the same number on every machine.
    println!("Tag::Zero as i32               = {}", Tag::Zero as i32);
    println!("Tag::One  as i32               = {}", Tag::One as i32);

    // A variant carrying data is a constructor *function*. Call it for a value.
    let Wrapped::Value(n) = Wrapped::Value(7);
    println!("Wrapped::Value(7) holds        = {n}");

    // `Wrapped::Value(0) as i32` is rejected -- a Wrapped is not an integer.
    // `Wrapped::Value as i32` is accepted, and is not a discriminant.
    let cast = Wrapped::Value as i32;
    let addr = Wrapped::Value as fn(i32) -> Wrapped as usize as i32;

    // The number is a truncated function address, so it differs from run to run
    // and can never be an answer key. What is fixed is what it equals.
    println!("cast is the function's address = {}", cast == addr);
}
```

Casting a constructed value is refused, so the accepted cast is easy to reach for by mistake:

```text title="Abridged — real rustc 1.98.0 output, without the --> header"
error[E0605]: non-primitive cast: `Wrapped` as `i32`
  |
6 |     let bad = Wrapped::Value(0) as i32;
  |               ^^^^^^^^^^^^^^^^^^^^^^^^ an `as` expression can be used to convert enum types to numeric types only if the enum type is unit-only or field-less
```

The compiler this library pins does not stay quiet about the accepted one. It builds, and warns:

```text
warning: direct cast of function item into an integer
   = note: `#[warn(function_casts_as_integer)]` on by default
help: first cast to a pointer `as *const ()`
```

That warning is a measurement, not a citation: `rustc 1.98.0`, [the pinned toolchain](../../05_Tooling/pinning_the_toolchain/README.md), on 2026-08-31. The study below recorded this issue as open against 1.93.0.

**This is the mildest of the thirty, and picked for that reason.** The behaviour is documented in the Reference; the reporter's complaint is that it *misleads*, not that it is unsafe. It earns a place in the dataset because nobody closed it as a non-bug — and it is here because it is the only one of the thirty that is still accepted, prints something deterministic, and fits in ten lines a beginner could have written by accident. Twelve of the thirty are still unfixed; the eleven that break memory safety need combinations of implied bounds, associated types, higher-rank bounds and trait objects that do not fit on a page, and seven of those eleven no longer compile at all — which is exactly what *fixed* means in the table below.

## The thirty

Sim, Ryu and Hong took every issue rustc's tracker carried between January 2022 and September 2025 under fourteen type-related area labels, kept the ones holding a snippet its reporter said should have been rejected, and added seven more recovered from an earlier survey of rustc bugs. Thirty.

| Consequence | Count | |
|---|---|---|
| Inconsistency | 17 | a snippet is accepted while a near-identical one is rejected |
| **Memory bug** | **11** | use-after-free and friends, reachable from safe code |
| Misleading behaviour | 1 | the runnable one above |
| Breaking change | 1 | an orphan `impl` slips through, so a benign library change breaks a client |

Most soundness bugs are not memory bugs. That is the finding worth carrying, and it cuts both ways: the guarantee is weaker than "safe code cannot segfault" — eleven times in three and a half years, it could — and the *bar* is higher, because the community treats an inconsistently-typed program as a bug on its own account. Of the thirty, **none** was closed as a non-bug.

Where they live, and what sets them off:

| | |
|---|---|
| affected feature | lifetimes 15 · traits 7 · type inference 6 · well-formedness 1 · casts 1 |
| triggering feature | associated types 15 · implied bounds 7 · `impl Trait` in return position 7 · trait objects 6 · higher-rank bounds 5 |
| status | fixed 18 · confirmed 4 · reported 8 · non-bug 0 |

Implied bounds trigger seven and **all seven break memory safety**; trait objects trigger six, and so do all six. Associated types are the most common trigger and rarely the cause — they are how an edge case in some *other* feature gets reached.

## They live for years

| From | To | Median |
|---|---|---|
| the feature stabilising | someone noticing | 1,079 days |
| someone noticing | a fix landing (of the 18 fixed) | 345 days |

Seven of the thirty were reachable the day the feature they need was stabilised. The longest gap between introduction and discovery was 3,552 days — most of Rust's life as a stable language.

Nothing here is a story about a slow project. It is what "requires a peculiar combination of features nobody writes, and then compiles cleanly" costs: there is no bug report, because there is no symptom, until someone goes looking on purpose.

## What it changes about how you write Rust

Nothing. You cannot avoid these, you will not meet one, and defensive coding against them is not a thing.

What it changes is the sentence you say out loud. *"Safe Rust cannot cause undefined behaviour"* is a claim about a design that has been proved for a model of the language. The compiler in front of you is an implementation of that design, and over three and a half years thirty programs it accepted were reported as ones it should have rejected — eleven of them able to corrupt memory. The honest version costs one clause: **safe Rust cannot cause undefined behaviour, and the eleven known exceptions since 2022 are compiler bugs with issue numbers, seven of them already fixed.**

Compare with what [C and C++](../../31_C_and_Cpp/README.md) offer, which is the comparison the claim is usually deployed in: there, undefined behaviour is reachable from ordinary code by design, is nobody's bug, and has no issue number to be fixed under. A soundness bug is an *implementation defect against a promise*. Having one at all requires having made the promise.

And the tool that catches the memory-bug half is one you can already run: applied to the eleven, [Miri](../../05_Tooling/nightly/README.md) and AddressSanitizer detected every one.

## If you are coming from another language

**Python.** There is nothing here to be unsound *about*. `mypy` is advisory — it is not in the path between your source and the interpreter, so "the type checker accepted a program it should have rejected" costs you a `TypeError` at run time, which is the normal way Python reports things. The nearest equivalent is a `ctypes` call or a C extension segfaulting the interpreter, and nobody files that as a violated guarantee, because none was made.

**ABAP.** Closer, and the comparison is instructive. The kernel really does enforce bounds, types and authority at run time, and the failure mode is a catchable `CX_SY_...` exception rather than corrupted memory — so ABAP's promise is kept by *checking during execution*, which cannot be got wrong by a type checker at all. Rust moves that same enforcement to compile time, which buys the runtime cost back and creates the failure mode on this page: a check that never runs cannot be skipped, but a check that runs at build time can be written wrong once and be wrong for nine years. A soundness bug is the price of the check having happened before the program shipped.

**C and C++.** UBSan and ASan are the same instruments used for the same job, and the difference is what a finding means. In C, a sanitizer report is a bug in *your* program. In Rust, a sanitizer report from a program with no `unsafe` in it is a bug in the *compiler*, and belongs on rust-lang/rust.

## Po polsku

**Sound** i **unsound** to nie to samo co „bezpieczny" i „niebezpieczny", a polszczyzna nie ma na tę parę ustalonego odpowiednika — „poprawny" gubi całą treść. Sens jest wąski i techniczny: *sound* znaczy „**nie istnieje** program, który to narzędzie przepuszcza, a który może wywołać niezdefiniowane zachowanie". To zdanie o **narzędziu**, nie o twoim kodzie. Błąd typu *soundness bug* w `rustc` to więc program **bez ani jednego `unsafe`**, który kompilator przyjął, choć powinien był odrzucić.

Trzy rzeczy warto rozdzielić, bo po polsku zlewają się w jedno. **Projekt języka** został udowodniony (RustBelt, dla formalnego modelu rdzenia Rusta) — to matematyka. **Implementacja**, czyli `rustc` na twoim dysku, to zwykły program, który ma tracker błędów. **Twoje własne API** nad blokiem `unsafe` to trzeci poziom i jedyny, na który masz wpływ. Strona [What `unsafe` turns off](../../09_Advanced/what_unsafe_turns_off/README.md) opisuje ten trzeci.

Liczby, które warto znać, zanim powtórzy się hasło „w bezpiecznym Ruście nic się nie może stać": w latach 2022–2025 zgłoszono **30** takich błędów, z czego **11** naprawdę łamie bezpieczeństwo pamięci, a pozostałe 17 to *niespójności* — kompilator przyjmuje fragment kodu, odrzucając niemal identyczny. Osiemnaście zostało naprawionych, żaden nie został zamknięty jako „to nie błąd". Mediana czasu od wprowadzenia funkcji do zauważenia błędu to **1 079 dni**, czyli blisko trzy lata: te błędy nie mają objawów, dopóki ktoś nie zacznie ich świadomie szukać.

Uczciwe polskie zdanie brzmi więc: *bezpieczny Rust nie może wywołać niezdefiniowanego zachowania, a jedenaście znanych wyjątków od 2022 roku to błędy kompilatora — z numerami zgłoszeń i, w większości, z poprawkami*. Różnica wobec C jest zachowana i jest to różnica gatunkowa: tam niezdefiniowane zachowanie jest **projektem**, osiągalnym ze zwykłego kodu, i nie ma numeru zgłoszenia, pod którym dałoby się je naprawić.

**Szukaj po polsku:** poprawność systemu typów · niezdefiniowane zachowanie · błąd kompilatora · `rust soundness bug` · `rustc I-unsound` · `RustBelt`
