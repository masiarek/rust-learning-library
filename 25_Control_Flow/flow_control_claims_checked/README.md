# What *Rust in Action* says about flow control, run

[Control flow](../README.md) › [Flow control](../flow_control/README.md) › **The book's claims, run**

**Level:** 101 · a companion to the section

**One line:** Twenty-one claims from §2.4 "Flow control" of *Rust in Action* (pp. 45–52), checked against rustc 1.98.0. Twelve hold as written and four hold with a condition. Five need a correction, and most of those are about *why* something happens rather than *what* happens.

The claims below are paraphrased. The section numbers and page numbers are the book's. Each row links to the lesson that teaches the construct in full.

Reading the ones that need more than the output:

- **1.** The book explains the error as the container's lifetime ending "once the block finishes". The array line shows that nothing ends for a `Copy` value, and the `v = vec![9]` line shows the name itself is still usable — what went away is the value, moved into the loop. The refusal below fires *inside* the loop body, before any block has finished.
- **2.** A `for` loop always calls `IntoIterator::into_iter` on what you give it. `&Vec` and `&HashMap` have an `IntoIterator` impl that happens to call `iter()`, so the table is right for them, but the equivalence is a promise each type makes, not a rule of the loop: `&String` makes no such promise.
- **5.** The index loop compiled, ran three passes against a `Vec` that ended with four items, and never saw the 4. `0..v.len()` is evaluated once, before the first pass.
- **6.** In a `for` loop, `continue` still moves the iterator on. In a `while` loop the increment is your own line, and a `continue` above it skips it: `i` stays at 1 until the guard stops the loop.
- **9.** `first_negative` is a `loop` with no `break` in it, left by `return` both times. `?` is a `return` in disguise, a panic unwinds out of it, and `std::process::exit` ends the process from inside it — without running destructors.
- **11.** `x` took the single value `0`. The innermost loop reached 1001 on the first `y`, so the outer loops never advanced.
- **13.** `goto` is an ordinary identifier. The words Rust keeps back for future use are a separate list in [the Reference ↗](https://doc.rust-lang.org/reference/keywords.html#reserved-keywords), and `goto` is not on it.
- **14.** In C, several failure points jump to one `cleanup:` label that frees what was acquired. In `open_both`, the early `return` drops `config`, and the success path drops `log` then `config`, in reverse order of creation. No label is involved. A labelled block with `break 'label` is the nearest Rust spelling of the jump itself, and [Loop labels](../loop_labels/README.md) shows it, but it is never needed for cleanup.
- **16.** The closure records each condition it is asked. `is(7)` was never called: the chain stopped at the first `true`.
- **17.** "Binding a name to a value" is `let`, and `let` is a statement, as the refusal below shows. But the book names the `=` as the thing that makes it one, and an `=` without `let` is an assignment *expression*: `let assigned = total = 5;` compiles, and `assigned` is `()`. The book's third form, declarations, also covers more than `fn`, `struct` and `enum`: every item is one, including `use`, `mod`, `const`, `static`, `impl` and `trait`.

## Claim 4, measured in assembly

The claim is about generated code, so it was checked in generated code: three functions summing a `&[u64]`, one indexing `0..v.len()`, one indexing `0..n` with `n` a separate argument, one iterating directly. Each was compiled with `rustc --edition 2024 -C opt-level=<0 or 3> --emit asm`, and every `panic_bounds_check` call inside each function was counted. The source and the counting script are on [Loops without an index](../loops_without_an_index/README.md).

```text title="Real run — rustc 1.98.0, 2026-09-16, identical on x86_64-apple-darwin and x86_64-unknown-linux-gnu"
opt-level=0  sum_by_len  calls panic_bounds_check: 1
opt-level=0  sum_by_n  calls panic_bounds_check: 1
opt-level=0  sum_by_iter  calls panic_bounds_check: 0
opt-level=3  sum_by_len  calls panic_bounds_check: 0
opt-level=3  sum_by_n  calls panic_bounds_check: 1
opt-level=3  sum_by_iter  calls panic_bounds_check: 0
```

So the check the book warns about is real in a debug build. With optimization on, it survives only where the compiler cannot prove the index is in range — and in `sum_by_n` even that one is a single comparison of `n - 1` against the length before the loop starts, not a check per element. Iterating directly never has one, at any level. The safety argument (claim 5) is the stronger reason to prefer it.

## Claim 21, read from the HIR

`RUSTC_BOOTSTRAP=1 rustc --edition 2024 -Zunpretty=hir while_in_hir.rs` prints the program after rustc has rewritten its loops, for a `while n < 3 { n += 1; }` followed by `for i in 0..2 { n += i; }`:

```text title="Real run — rustc 1.98.0, 2026-09-16, the body of main"
    let mut n = 0;
    loop { if n < 3 { n += 1; } else { break; } }
    {
        let _t =
            match into_iter(Range { start: 0, end: 2 }) {
                mut iter =>
                    loop {
                        match next(&mut iter) {
                            None {} => break,
                            Some {  0: i } => { n += i; }
                        }
                    },
            };
        _t
    }
```

Every loop is a `loop` underneath. The `for` loop is built from `match`, and so is `?`, but the `while` loop is built from `if`. [Printing the HIR](../../20_Compilers/printing_the_hir/README.md) walks through the `for` and `?` rewrites line by line.

## Tests for anything else you read about flow control

- **Does it say *why* a value is gone after a loop?** The answer is a move into `into_iter`, visible inside the loop body. An explanation in terms of lifetimes ending or blocks finishing will mislead you about arrays and references.
- **Does it treat `for x in &c` as a language rule?** It is an impl on `&C`, and a type can lack one.
- **Does it say `while true` and `loop` differ only in style?** Try assigning a variable inside each and using it after.
- **Does it list `break` as the only way out of a loop?** Count `return`, `?`, a panic and `process::exit`.
- **Does it call a missing `match` arm a warning?** It is `E0004`. The unreachable-arm check is the one that is a warning.
- **Does it recommend labels or `goto`-like jumps for cleanup?** In Rust that is `Drop`.

## Po polsku

Sekcja 2.4 książki *Rust in Action* dobrze opisuje, **co** robią pętle i rozgałęzienia. Kiedy wyjaśnia, **dlaczego** tak się dzieje, bywa nieprecyzyjna. Sprawdziliśmy 21 twierdzeń z tej sekcji na rustc 1.98.0: dwanaście jest prawdziwych, cztery są prawdziwe pod warunkiem, a pięć wymaga poprawki. Najważniejsza poprawka dotyczy pętli `for`. Po `for item in container` wektora nie da się użyć nie dlatego, że po zakończeniu bloku „skończył się jego czas życia”. Pętla **przenosi** go do `into_iter` już w pierwszej linii, więc błąd `E0382` pojawia się nawet w ciele pętli. Tablica `[1, 2, 3]` typu `Copy` zostaje nietknięta, a samej nazwie można później przypisać nową wartość.

Pozostałe poprawki są krótsze. `loop` kończy się nie tylko przez `break`, ale też przez `return`, `?`, panikę albo `process::exit`. Sprzątanie w stylu C (skok do etykiety `cleanup:`) robi w Ruscie `Drop`, a nie etykieta pętli. Brakujące ramię `match` to błąd `E0004`, a nie ostrzeżenie. Wreszcie `while` pod spodem to `loop` z `if`, a nie z `match`. Do tego jedno zastrzeżenie: instrukcją jest `let`, ale samo przypisanie `x = 5` (bez `let`) jest wyrażeniem typu `()`. Porada, żeby zamiast `while true` pisać `loop`, jest słuszna i nie chodzi tylko o styl. Kompilator ostrzega (`while_true`), nie uzna zmiennej przypisanej w `while true` za zainicjowaną (`E0381`) i nie pozwoli, by funkcja zwracająca `i32` kończyła się taką pętlą (`E0308`).
