# `while` loops

**Level:** 101 · for newcomers

**One line:** `while` repeats a block for as long as a `bool` condition holds and checks it **before** every pass — the loop for a count nobody knows in advance, and the one that needs a `mut` declared outside it to make any progress.

```rust
fn main() {
    let mut n = 3;
    while n > 0 {
        println!("{n}");  // 3, then 2, then 1
        n -= 1;
    }
    println!("liftoff at n = {n}");  // liftoff at n = 0
}
```

No parentheses around the condition, braces the body cannot drop, and an `n` that is `mut` and declared *outside* the loop — the body's only way to end the loop is to change something the condition reads.

## The condition is a `bool`, and the rules are `if`'s rules

| Written | What rustc 1.98.0 does |
|---|---|
| `while n { … }` with `n` an integer | `error[E0308]: mismatched types` — expected `bool`, found integer |
| `while (n > 0) { … }` | compiles, with an `unused_parens` warning: *unnecessary parentheses around* the condition |
| `while n > 0 n -= 1;` | a parse error, expected `{` — a one-statement body still needs braces |

There is no truthiness to fall back on: not `0`, not an empty `Vec`, not `None`. [Meet the `bool`](../../15_First_Programs/meet_the_bool/README.md) has the whole rule, and [`if` expressions](../if_expressions/README.md) the same three rules for a branch. For a loop the translations are `while n != 0`, `while !queue.is_empty()`, and — for *while there is another item* — [`while let`](../../17_Option_and_Result/while_let/README.md).

## The check comes first, so zero passes is a possible answer

Part 1 above runs the same countdown from `0`, and the body runs **zero** times. C's `do { … } while (n > 0);` would have run it once before asking; Rust has no `do … while` at all. The shape it becomes is a [`loop`](../the_loop_keyword/README.md) with the condition, negated, as the way out at the bottom:

```rust
loop {
    n -= 1;
    passes += 1;
    if n <= 0 {
        break;  // the do...while condition, negated
    }
}
```

From `n = 0` that runs once and leaves `n` at `-1` — the third line of part 1. The question that picks between the two: must the body run before there is anything to test (a first attempt, a first line read)? Then `loop`; otherwise `while`.

## Progress is a `mut` you declare outside the loop

*Rust in Action* §2.4.3 sketches a loop that collects ten samples from a sensor and skips outliers with `continue` — a fragment, since the sensor is never defined. Part 2 above is the same loop over a fixed table of readings:

```rust
while samples.len() < 5 && next < readings.len() {
    let sample = readings[next];
    next += 1;  // before the `continue`, or an outlier is re-read forever
    if is_outlier(sample) {
        skipped += 1;
        continue;
    }
    samples.push(sample);
}
```

`samples`, `next` and `skipped` are all `mut` and all declared above the loop, because the condition and the report after the loop both need them. The table changed two things:

- **A second condition.** A sensor never runs out; a table does, and `readings[next]` past its end panics. Once a `while` needs `next < readings.len()` as well, the data is a sequence — and the last line of part 2 gets the same five samples from `readings.iter().copied().filter(..).take(5)`, with no `mut`, no index and no second condition.
- **Where `next += 1` sits.** Move it below the `continue` and the first outlier is read again on every pass, forever. A `for` loop cannot make that mistake, because its iterator advances whether or not the body reaches the end; [`continue` expressions](../continue_expressions/README.md) has that trap in full.

## A `while` loop evaluates to `()`

`while` is an expression like every other [block-shaped thing in Rust](../../15_First_Programs/a_block_is_an_expression/README.md), and its value is always `()` — part 3 binds it to prove it. Whatever a `while` loop computes lives in a `mut` declared above it. `break n;` inside a `while` is `E0571`, *`break` with value from a `while` loop*: carrying a value out is [`loop`'s job](../the_loop_keyword/README.md#break-carries-the-value-out-and-only-loop-takes-one), and the reason `while true` is no substitute for it.

## Listing 2.7: a condition that is not a sequence

The book's Listing 2.7 counts how many times it can add one before a second has passed. Part 4 above runs it with a 10 ms limit:

```rust
let time_limit = Duration::from_millis(10);  // the book: Duration::new(1, 0)
let mut count: u64 = 0;
let start = Instant::now();
while (Instant::now() - start) < time_limit {
    count += 1;
}
```

This is `while` at its most honest: no collection to walk and no pass count to predict, only a condition that turns false at some moment. (The parentheses around the subtraction are optional, since `-` binds tighter than `<`, and unlike parentheses around the whole condition they draw no warning.)

Part 4 prints only what holds on every run — the loop ran at least once, and stopped no earlier than the limit. The count itself changes every run. Measured once, on the Intel Mac this page was written on: about 220,000 passes in 10 ms, and calling `Instant::now()` that many times on its own took about 9 of those 10 ms. So the number mostly measures how fast the clock answers, not how fast `count += 1` is — the gap between a loop with a timer in it and a benchmark. [Time and benchmarking](../../33_Time_and_Benchmarking/README.md) is the section about the second: why [`Instant - Instant` saturates to zero](../../33_Time_and_Benchmarking/an_instant_is_not_a_system_time/README.md) rather than panicking (so the listing's subtraction cannot panic on 1.98), why [a `Duration` cannot be negative](../../33_Time_and_Benchmarking/a_duration_cannot_be_negative/README.md), and what [`black_box`](../../33_Time_and_Benchmarking/black_box_is_a_hint/README.md) does and does not stop the optimizer from deleting.

## The trap: a condition the body never moves

A `while` loop ends only when its body changes something its condition reads. Forget to, and the result is an infinite loop that is valid Rust. What the tools notice depends on the shape of the mistake — measured with rustc and clippy 1.98.0:

| The mistake | rustc | clippy |
|---|---|---|
| `i` never changes; `while i < limit` | `unused_mut` warning | [`while_immutable_condition` ↗](https://rust-lang.github.io/rust-clippy/rust-1.98.0/index.html#while_immutable_condition) — an **error**, deny by default |
| `i` never changes; `while i < readings.len()` | `unused_mut` warning | nothing more: the same loop with a method call in its condition is not flagged |
| `i` changes on some passes only — a `continue` above `i += 1` | nothing | nothing |

The `unused_mut` warning is rustc's only hint, and it is a good one: a `mut` binding that nothing mutates is exactly what a forgotten `i += 1` leaves behind.

```text title="Abridged — real rustc output for forgot_to_advance.rs"
warning: variable does not need to be mutable
 --> forgot_to_advance.rs:3:9
  |
3 |     let mut i = 0;
  |         ----^
  |         |
  |         help: remove this `mut`
  |
  = note: `#[warn(unused_mut)]` (part of `#[warn(unused)]`) on by default
```

The third row is the one nothing catches, and part 5 above is the way around it: `while i < prices.len() { … i += 1; }` is a `for` loop in disguise, with two `mut`s and an index where `for price in prices` has one `mut` and no index to forget. Reach for `while` when the condition is not a sequence — a time limit, a value converging, input arriving until it stops, a work list the body [drains and refills](../../24_Iterators/when_a_loop_beats_a_chain/README.md) — and for `for` whenever it is.

## If you are coming from another language

**Python.** `while cond:` is the same loop — tested before every pass, and Python has no `do … while` either. Three habits need translating. **Truthiness**: `while queue:` becomes `while !queue.is_empty()` and `while n:` becomes `while n != 0`, because the condition must be a `bool`. **The walrus loop**: `while (item := next_item()):` assigns and tests truthiness in one line, so a legitimate `0` or `""` ends it early; Rust's counterpart, `while let Some(item) = next_item()`, tests a *shape*, and a `Some(0)` keeps the loop going. **`while … else:`** has no counterpart — Python runs the `else` when the loop ends without a `break`, and Rust's loops take no `else`; when the way out matters, write a [`loop`](../the_loop_keyword/README.md) whose `break` carries a value. What the compiler adds is the `bool` rule and nothing about termination: an infinite `while` is as quiet in Rust as in Python, apart from the lints in the table above.

**C.** The same loop with its punctuation moved: C requires the parentheses and lets you drop the braces, Rust warns about the parentheses and will not parse without the braces. Three C idioms do not survive. `while (n)` on an integer or a pointer is `E0308` — write the comparison. `do { … } while (cond);` does not exist — use `loop` with the negated condition at the bottom, as above. And assignment inside the condition, `while ((c = getchar()) != EOF)`, is a type error, because a Rust assignment evaluates to `()` rather than to the value assigned:

```text title="Abridged — real rustc output for assign_in_condition.rs"
error[E0308]: mismatched types
 --> assign_in_condition.rs:5:29
  |
5 |     while (c = input[i]) != -1 {
  |           --------------    ^^ expected `()`, found integer
  |           |
  |           expected because this is `()`
```

The replacement is `while let`, where the pattern does the assigning and the matching does the testing. What transfers exactly is the hazard: an index loop that forgets its increment hangs in both languages, and neither compiler refuses it.

**ABAP.** `WHILE lv_count > 0. … ENDWHILE.` is this loop: tested before each pass, zero passes possible, and no post-test loop in ABAP either. An ABAP condition was already a logical expression rather than a field — there is no boolean type to put there — so the `bool` rule costs nothing. What changes:

- **No `sy-index`.** Inside `DO` and `WHILE`, ABAP counts the passes for you in `sy-index`. Rust's `while` counts nothing; the pass number is a `mut` you declare, and needing one is often the sign the loop wanted to be a [`for`](../for_loops/README.md) with [`enumerate`](../../24_Iterators/zip_and_enumerate/README.md) — `DO n TIMES` is `for _ in 0..n` already.
- **`CHECK` inside a loop is `if !cond { continue; }`.** A failed `CHECK` ends the current pass, so it carries the same trap as `continue`: a `CHECK` above the statement that moves the condition's variable loops forever, in ABAP and in Rust.
- **`EXIT` is `break` and `CONTINUE` is `continue`** — both transfer by name. The loop they most often sit in, `DO. … ENDDO.` with an `EXIT`, is Rust's [`loop`](../the_loop_keyword/README.md), not a `while`.

## Practice

**Collatz, with a `while` that has to earn its exit.** The Collatz step count of a number is how many steps it takes to reach 1, halving it when even and replacing it with `3n + 1` when odd. Write `fn collatz_steps_u32(start: u32) -> Option<u32>` with a `while n != 1` loop, and print the counts for 1, 6, 7, 27 and 97.

Then two inputs that break the naive version, one each. **Before running anything**, say what `while n != 1` does when `start` is `0`, and add the one line that stops it. Then run `159_487`: nothing about that input is large, but somewhere on its way to 1 the value no longer fits a `u32` — make the function return `None` there instead of panicking (a debug build: *attempt to multiply with overflow*) or wrapping (an `-O` build of the unchecked version reports 245 steps; the true count is 183), and confirm with a `u64` version that the sequence itself is fine. Finish with a `while` loop that finds the first start whose climb leaves `u32` — a loop whose pass count nobody knows in advance. [The width that runs out](../../15_First_Programs/values/README.md#practice) is the same lesson from the other side.

```rust
//! Kata solution: Collatz step counts with `while`, the input that never
//! reaches the exit condition, and the width that runs out on the way.
//!
//!   rustc --edition 2024 while_loops_kata.rs -o /tmp/wlk && /tmp/wlk

/// Steps from `start` to 1, or `None` when the sequence cannot get there
/// in a `u32`: 0 never reaches 1, and some starts climb past `u32::MAX`.
fn collatz_steps_u32(start: u32) -> Option<u32> {
    if start == 0 {
        return None; // 0 / 2 == 0: `while n != 1` would never become false
    }
    let mut n = start;
    let mut steps = 0;
    while n != 1 {
        n = if n % 2 == 0 {
            n / 2
        } else {
            n.checked_mul(3)?.checked_add(1)?
        };
        steps += 1;
    }
    Some(steps)
}

fn collatz_steps_u64(start: u64) -> Option<u64> {
    if start == 0 {
        return None;
    }
    let mut n = start;
    let mut steps = 0;
    while n != 1 {
        n = if n % 2 == 0 {
            n / 2
        } else {
            n.checked_mul(3)?.checked_add(1)?
        };
        steps += 1;
    }
    Some(steps)
}

fn peak_u64(start: u64) -> u64 {
    let mut n = start;
    let mut peak = n;
    while n != 1 {
        n = if n % 2 == 0 { n / 2 } else { 3 * n + 1 };
        peak = peak.max(n);
    }
    peak
}

fn main() {
    println!("1. Steps to reach 1");
    for start in [1, 6, 7, 27, 97] {
        println!("   start {start:>3}: {:?}", collatz_steps_u32(start));
    }
    println!("   start 1 is Some(0): the condition is false before the first pass.");

    println!();
    println!("2. The start that never reaches the exit condition");
    println!("   start   0: {:?}", collatz_steps_u32(0));
    println!("   0 is even, 0 / 2 is 0, and `while n != 1` stays true forever.");
    println!("   The early return is the only thing between this call and a hang.");

    println!();
    println!("3. The width that runs out");
    let start = 159_487;
    println!("   u32 start {start}: {:?}", collatz_steps_u32(start));
    println!("   u64 start {start}: {:?}", collatz_steps_u64(start as u64));
    println!("   peak on the way  = {}", peak_u64(start as u64));
    println!("   u32::MAX         = {}", u32::MAX);
    println!("   Nothing in the input is large. The climb is.");

    println!();
    println!("4. The first start whose climb leaves u32");
    let mut candidate: u32 = 1;
    while collatz_steps_u32(candidate).is_some() {
        candidate += 1;
    }
    println!("   {candidate}   (found by a while loop whose count nobody knew in advance)");
}
```

## Po polsku

`while` sprawdza warunek **przed** każdym obiegiem, więc może nie wykonać się ani razu — a pętli z warunkiem na końcu, czyli pascalowego `repeat … until` i C-owego `do…while`, w Ruscie po prostu nie ma; jej odpowiednikiem jest `loop { …; if !warunek { break; } }`. Obowiązują tu te same trzy reguły co przy `if`: żadnych nawiasów wokół warunku (kompilator ostrzega `unused_parens`), klamry obowiązkowe (bez nich jest błąd składni), a warunek musi być typu `bool` — `while n` dla liczby całkowitej to `E0308`. Sama pętla też jest wyrażeniem, ale jej wartością jest zawsze `()`: wynik obliczony w `while` mieszka w zmiennej `mut` zadeklarowanej przed pętlą, a `break n;` w środku `while` to błąd `E0571`. Wartość z pętli wynosi tylko `loop`.

Warto zwrócić uwagę na kształt takiego kodu: `while` niemal zawsze potrzebuje zmiennej `mut` zadeklarowanej przed pętlą, i to jest dokładnie ten wzorzec, którego `for` po iteratorze pozwala uniknąć. Stąd pułapka — jeśli ciało zapomni posunąć zmienną z warunku, powstaje pętla nieskończona, która jest poprawnym programem w Ruscie. Zmierzone narzędzia widzą ją różnie: rustc daje tylko ostrzeżenie `unused_mut` (zmienna `mut`, której nic nie zmienia, to właśnie ślad po zapomnianym `i += 1`), clippy zgłasza błąd `while_immutable_condition` dla `while i < limit`, ale już nie dla `while i < readings.len()`, a zmiennej przesuwanej tylko w części obiegów — `continue` postawione nad `i += 1` — nie zauważa nikt. Wersja z `for` nie ma indeksu, o którym można zapomnieć.

`while` jest uczciwym wyborem wtedy, gdy warunek nie jest sekwencją: limit czasu, wartość, która zbiega, dane napływające do końca, lista zadań opróżniana i uzupełniana w tej samej pętli. Listing 2.7 z *Rust in Action* liczy obiegi do upływu limitu czasu; liczba obiegów jest inna przy każdym uruchomieniu, więc przykład drukuje tylko to, co prawdziwe zawsze (`count > 0`, `elapsed >= time_limit`), a sama liczba mierzy głównie szybkość odczytu zegara — to pętla z zegarem, a nie benchmark. Ćwiczenie z ciągiem Collatza pokazuje obie pułapki naraz: dla `0` warunek `n != 1` nigdy nie staje się fałszywy, a start `159 487` po drodze przekracza `u32::MAX`, choć sam jest mały.
