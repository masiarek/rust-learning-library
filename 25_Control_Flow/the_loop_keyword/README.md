# `loop`

**Level:** 101 → 201 · for newcomers

**One line:** `loop` repeats forever and is left with `break` — and because `break` can carry a value, `loop` is the one loop in Rust that is routinely used as an **expression**: `let x = loop { … break v; };`.

```rust
fn main() {
    let responses = [503, 503, 200];
    let mut attempts = 0;
    let status = loop {
        let code = responses[attempts];
        attempts += 1;
        if code == 200 {
            break code;
        }
    };
    println!("{status} after {attempts} attempts");  // 200 after 3 attempts
}
```

No condition at the top, so nothing ends the loop except what the body does. `break code` ends it *and* hands `code` to the `let` — no result variable declared above the loop, no `Option` placeholder to fill in later.

## `break` carries the value out, and only `loop` takes one

Part 1 above is the retry loop from the top of the page. Try the same `break code;` in a `while` or a `for` and rustc refuses:

```text title="Abridged — real rustc output for while_value.rs"
error[E0571]: `break` with value from a `while` loop
 --> while_value.rs:5:9
  |
3 |     let x = while n < 3 {
  |             ----------- you can't `break` with a value in a `while` loop
4 |         n += 1;
5 |         break n;
  |         ^^^^^^^ can only break with a value inside `loop` or breakable block
  |
help: use `break` on its own without a value inside this `while` loop
  |
5 -         break n;
5 +         break;
```

A `for` loop gets the same `E0571`, worded *`break` with value from a `for` loop*. The reason is in what else can end those loops: a `while` also stops when its condition turns false, and a `for` when its iterator runs out — no `break` ran, so there would be no value. A `loop` has no condition to run out of, so every way it finishes normally is a `break`, and every `break` can agree on a type. (The *breakable block* in the label is the other place a value can leave: `let found = 'search: { … break 'search Some(i); … None };` — see [loop labels](../loop_labels/README.md) and [`break` expressions](../break_expressions/README.md).)

## A `loop` nothing breaks out of has type `!`

The Reference states it in one line: a `loop` with no associated `break` is *diverging* and has type [`!`](../../15_First_Programs/the_never_type/README.md). Control never reaches the end of it, so the compiler lets it stand where any type is expected:

```rust
fn first_success(responses: &[u16]) -> Option<usize> {
    let mut i = 0;
    loop {
        if i == responses.len() {
            return None;
        }
        if responses[i] == 200 {
            return Some(i + 1);
        }
        i += 1;
    }
}
```

The function's whole body is that `loop`, and it never `break`s — it only `return`s — so its type is `!`, which coerces to the `Option<usize>` the signature promised. No trailing `None` after the loop, and none needed. The extreme case compiles too: `let x: i32 = loop {};` is accepted, with two warnings, *unreachable statement* for whatever follows it and *unused variable* for `x`, which can never be given a value.

## `while true` is not `loop`, and rustc says so three ways

`while true { … }` runs exactly like `loop { … }`. The book notes that Rust programmers avoid it without saying why; the compiler gives three reasons, and only the first is style.

**A warning, on by default:**

```text title="Abridged — real rustc output for while_true.rs"
warning: denote infinite loops with `loop { ... }`
 --> while_true.rs:3:5
  |
3 |     while true {
  |     ^^^^^^^^^^ help: use `loop`
  |
  = note: `#[warn(while_true)]` on by default
```

**A binding assigned inside it is not initialised after it.** `let x: i32; while true { x = 1; break; } println!("{x}");` is refused; the same code with `loop` compiles and prints `1`:

```text title="Abridged — real rustc output for while_true_init.rs, without the while_true warning"
error[E0381]: used binding `x` is possibly-uninitialized
 --> while_true_init.rs:7:16
  |
2 |     let x: i32;
  |         - binding declared here but left uninitialized
3 |     while true {
  |           ---- if this condition isn't met and the `while` loop runs 0 times, `x` is not initialized
...
7 |     println!("{x}");
  |                ^ `x` used here but it is possibly-uninitialized
  |
  = note: when checking initialization, the compiler describes possible control-flow paths without evaluating whether branch conditions can actually have the values shown
```

That note is the whole explanation. The initialization check reads a `while` as *test, then maybe run the body*, and it does not look at what the test is — not even the literal `true`. A `loop` has no test, so the only path to `println!` goes through `x = 1`. The rule being enforced — [a binding must be assigned on every path before it is read](../../17_Option_and_Result/initial_values/README.md) — is the same one behind [uninitialized reads](../../31_C_and_Cpp/uninitialized_reads/README.md).

**A function whose body is `while true` does not return its type.** `fn first() -> i32 { while true { return 1; } }` is refused; with `loop` it compiles:

```text title="Abridged — real rustc output for while_true_return.rs, without the while_true warning"
error[E0308]: mismatched types
 --> while_true_return.rs:2:5
  |
1 |   fn first() -> i32 {
  |                 --- expected `i32` because of return type
2 | /     while true {
3 | |         return 1;
4 | |     }
  | |_____^ expected `i32`, found `()`
  |
  = note: `while` loops evaluate to unit type `()`
help: consider returning a value here
  |
4 ~     }
5 +     /* `i32` value */
  |
```

A `while` loop's type is `()` whatever its condition says, and `()` is not `i32`. A `loop` with no `break` has type `!`, which coerces to `i32` like it coerces to anything.

## Every way out of a `loop`

The book describes `loop` as running until a `break` or until the program is terminated from outside. Those are two of the exits; part 4 above runs five, all from inside the loop body:

| Exit | Where control goes | Part 4 shows |
|---|---|---|
| `break` / `break value` | to the code after the loop, with the value | `status = 200` |
| `return` | out of the enclosing function | `first_success` above, both `Some(2)` and `None` |
| [`?`](../../17_Option_and_Result/the_question_mark_operator/README.md) | out of the enclosing function, with the `Err` or `None` | `parse_all` stopping at `"x"` |
| a panic | unwinds out of the loop and the function, until something catches it | `gave up after 3 passes`, caught by [`catch_unwind`](../../17_Option_and_Result/what_a_panic_costs/README.md) |
| [`std::process::exit` ↗](https://doc.rust-lang.org/std/process/fn.exit.html) | nowhere — the process ends | the last line of the output, printed on pass 2 |

`break 'outer` from a nested loop is a sixth, and [loop labels](../loop_labels/README.md) has it. `continue` is not an exit: it starts the next pass.

## The shapes it is for: retry, and read until a sentinel

Part 1 is **retry until success**. Part 2 is the shape the book draws for a long-running server — accept a request, process it, respond, repeat — over a fixed table, with a sentinel that ends it:

```rust
loop {
    let request = requests[next];  // accept
    next += 1;
    if request == "QUIT" {
        break;
    }
    handled.push(request);  // process and respond
}
```

Both have a first attempt that must happen before there is anything to test, which is what makes them `loop`s and not `while`s — the same reasoning that turns C's `do … while` into [a `loop` with its test at the bottom](../while_loops/README.md#the-check-comes-first-so-zero-passes-is-a-possible-answer). Both also index a table that could run out: part 1 panics if no `200` ever arrives, and part 2 if `QUIT` never does. A real retry loop needs a budget, which is the kata below.

## Where a `loop` becomes `while let` or an iterator

Part 3 above gets both answers with no `mut`, no index and no `break`: `responses.iter().position(..)` for the retry, and `requests.iter().take_while(..)` for the sentinel. When the data is already a sequence, that is the usual better ending.

The in-between case is a `loop` whose first statement pulls the next item and `break`s when there is none. Clippy's `while_let_loop` lint, a warning by default, names the rewrite:

```text title="Abridged — real clippy-driver output for while_let_loop.rs, second warning only"
warning: this loop could be written as a `while let` loop
  --> while_let_loop.rs:12:5
   |
12 | /     loop {
13 | |         let Some(line) = it.next() else { break };
14 | |         println!("{line}");
15 | |     }
   | |_____^ help: try: `while let Some(line) = it.next() { .. }`
```

The mirror-image mistake is a `loop` that `break`s on every path of its first pass, so it never repeats. That one is [`never_loop` ↗](https://rust-lang.github.io/rust-clippy/rust-1.98.0/index.html#never_loop), which clippy denies by default: *this loop never actually loops*. Both lints are clippy's: plain `rustc` compiles `while_let_loop.rs` without a single warning.

## If you are coming from another language

**Python.** `while True:` with a `break` is Python's `loop`, and the translation is one keyword. What does not transfer is getting a value out. Python's `break` carries nothing, so the result goes in a variable declared before the loop — usually `status = None` — and the code after the loop has to trust that something overwrote it. `let status = loop { … break code; };` makes that assignment part of the loop's type: every `break` must supply an `i32`, and there is no `None` placeholder to forget. Python's other answer, `next(code for code in responses if code == 200)`, is part 3's iterator version, and like `position` it has to say what happens when nothing matches (a `StopIteration`, or a default argument). Python's `while … else:` runs its `else` when the loop ends *without* a `break`; a Rust `loop` cannot end that way, which is exactly why its `break` is allowed to carry a value.

**C.** `for (;;)` and `while (1)` are C's `loop`, and C has no rule that tells them apart from any other loop — so the compiler is left to spot the constant. Measured with Apple clang 21 and `-Wall -Wextra`: `int first(void) { while (1) { return 1; } }` and `int x; while (1) { x = 1; break; } printf("%d", x);` compile **without a warning**, because clang sees that `1` is never false; change the condition to a parameter `k` and `-Wreturn-type` warns *non-void function does not return a value in all control paths*. rustc takes the opposite position on purpose — its initialization and type checks do not evaluate the condition, as the `E0381` note above says — and gives the infinite loop its own keyword instead, so the guarantee does not depend on how clever the analysis is. C's `break` carries no value either; the result goes through a variable declared outside, as in Python.

**ABAP.** `DO. … ENDDO.` without `TIMES` is ABAP's `loop`, and `EXIT` is its `break` — both transfer directly, including that `EXIT` leaves only the innermost loop. Three differences:

- **No value leaves with `EXIT`.** The ABAP pattern fills a variable and then exits — `lv_status = ls_response-code. EXIT.` — so the value and the exit are two statements that can drift apart. `break code` is one.
- **The other exits exist too, under other names.** `RETURN` leaves the method or procedure from inside the `DO`, as `return` does; `RAISE EXCEPTION` unwinds out of it, the nearest thing to a panic or an early `?`; `LEAVE PROGRAM` ends the program, like `process::exit`.
- ***Terminated from outside* is the ABAP runtime's job.** A `DO` with no reachable `EXIT` in a dialog work process runs until the maximum runtime is reached and the work process is ended with a `TIME_OUT` short dump. Rust has no such supervisor: a `loop` with no exit runs until someone kills the process, and what the compiler adds instead is the type `!`, which records in the program that control never comes back.

## Practice

**Retry with a budget.** A server answers from a fixed table — `[503, 503, 200]` — and returns `503` for every attempt after the table runs out. Write `fn retry_loop(responses: &[u16], budget: usize) -> Result<usize, usize>` as a `loop` whose `break` carries the whole answer: `Ok(attempt number)` on the first `200`, `Err(attempts made)` once the budget is spent. Print it for budgets 3, 5, 2 and 1.

Then **predict before running**: with a budget of `0`, how many requests does your loop send? Write a second version that sends none, and a third with no `loop` at all, built from `(0..budget)` and `position`. Finally, replace your `>=` against the budget with `==`, call it with a budget of `0` against a server that never succeeds — behind a safety cap — and explain what you see.

```rust
//! Kata solution: retry with a budget, as a `loop` whose `break` carries a
//! `Result` — and the budget of 0 that decides where the check belongs.
//!
//!   rustc --edition 2024 the_loop_keyword_kata.rs -o /tmp/tlkk && /tmp/tlkk

/// A server that answers from a fixed table, then keeps failing.
fn fetch(responses: &[u16], attempt: usize) -> u16 {
    responses.get(attempt).copied().unwrap_or(503)
}

/// Check at the bottom: the body runs before the budget is looked at.
fn retry_loop(responses: &[u16], budget: usize) -> Result<usize, usize> {
    let mut attempts = 0;
    loop {
        let code = fetch(responses, attempts);
        attempts += 1;
        if code == 200 {
            break Ok(attempts);
        }
        if attempts >= budget {
            break Err(attempts);
        }
    }
}

/// Check at the top: a budget of 0 sends nothing.
fn retry_checked_first(responses: &[u16], budget: usize) -> Result<usize, usize> {
    let mut attempts = 0;
    loop {
        if attempts >= budget {
            break Err(attempts);
        }
        let code = fetch(responses, attempts);
        attempts += 1;
        if code == 200 {
            break Ok(attempts);
        }
    }
}

/// The same bottom check written with `==`, run with a safety cap so the
/// program can report what it would have done instead of doing it.
fn retry_equals_capped(responses: &[u16], budget: usize, cap: usize) -> Result<usize, usize> {
    let mut attempts = 0;
    loop {
        let code = fetch(responses, attempts);
        attempts += 1;
        if code == 200 {
            break Ok(attempts);
        }
        if attempts == budget || attempts == cap {
            break Err(attempts);
        }
    }
}

fn retry_iter(responses: &[u16], budget: usize) -> Result<usize, usize> {
    (0..budget)
        .position(|attempt| fetch(responses, attempt) == 200)
        .map(|i| i + 1)
        .ok_or(budget)
}

fn main() {
    let responses = [503, 503, 200];
    println!("responses = {responses:?}, then 503 forever");
    println!();
    println!("budget   check at bottom   check at top   iterator");
    for budget in [3, 5, 2, 1, 0] {
        println!(
            "{budget:>6}   {:<15}   {:<12}   {:?}",
            format!("{:?}", retry_loop(&responses, budget)),
            format!("{:?}", retry_checked_first(&responses, budget)),
            retry_iter(&responses, budget),
        );
    }
    println!();
    println!("Budget 0 is the only row where the columns disagree. With the check");
    println!("at the bottom the loop is a do...while: one request goes out before");
    println!("anyone asks whether it was allowed.");
    println!();
    let failing = [503];
    println!("Now `attempts == budget` instead of `>=`, against a server that never succeeds:");
    println!("   budget 3: {:?}", retry_equals_capped(&failing, 3, 10_000));
    println!("   budget 0: {:?}   <- stopped by the 10_000 cap, not by the budget", retry_equals_capped(&failing, 0, 10_000));
    println!("attempts is already 1 when it is first compared, so 1 == 0 is the first");
    println!("of an endless run of false answers.");
}
```

## Po polsku

`loop` kręci się w nieskończoność i wychodzi się z niego przez `break` — i tylko w tej jednej pętli `break` potrafi nieść wartość, dzięki czemu `let x = loop { … break v; };` w ogóle ma sens; `while` i `for` zawsze dają `()`, a `break n;` w ich środku to błąd `E0571`. Powód jest prosty: `while` może się skończyć, bo warunek stał się fałszywy, a `for`, bo iterator się wyczerpał — wtedy żaden `break` się nie wykonał i nie byłoby skąd wziąć wartości. `loop` nie ma warunku, więc każde normalne zakończenie to `break`.

Polskie kursy programowania uczą zwykle pętli nieskończonej jako `while (true)`, ale w Ruscie to nie jest ta sama konstrukcja i nie chodzi tu tylko o styl. Kompilator mówi to na trzy sposoby: ostrzeżenie `while_true` („denote infinite loops with `loop`”), błąd `E0381` dla zmiennej przypisanej wewnątrz `while true` i czytanej za pętlą (analiza inicjalizacji celowo **nie oblicza** warunku, nawet literału `true`, więc zakłada, że pętla mogła wykonać się zero razy), oraz błąd `E0308` dla funkcji, której ciałem jest `while true { return 1; }` — pętla `while` ma typ `()`. Ta sama funkcja z `loop` się kompiluje, bo pętla bez `break` ma typ `!` (*never*), który pasuje w miejsce każdego typu; dlatego kompiluje się nawet `let x: i32 = loop {};`, z dwoma ostrzeżeniami.

Książka *Rust in Action* mówi, że z `loop` wychodzi się przez `break` albo przez zabicie programu z zewnątrz. Wyjść jest więcej: `return`, operator `?`, panika i `std::process::exit` — przykład pokazuje wszystkie, każde z wnętrza pętli. Typowe zastosowania to „próbuj, aż się uda” i czytanie do napotkania wartownika (kształt serwera: przyjmij, obsłuż, odpowiedz); jeśli dane są już sekwencją, lepszym zakończeniem bywa iterator (`position`, `take_while`), a pętlę, która na początku pobiera element i robi `break` przy jego braku, `clippy` sam każe zamienić na `while let`. Dla programisty ABAP-a: `DO. … ENDDO.` z `EXIT` to dokładnie `loop` z `break`, tyle że `EXIT` nie niesie wartości, a nieskończony `DO` kończy za nas środowisko uruchomieniowe zrzutem `TIME_OUT`.
